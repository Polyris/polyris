# Polyris — відповідність компонентно-плагінній архітектурі (з транскрипту)

База: чиста початкова версія `polyris-main` @ v0.91.0.

Транскрипт описує: **скелет-фреймворк із реєстром + точками розширення**; компоненти
самі себе реєструють на імпорті; **explicit** перелік модулів-плагінів; опен-сорсні
компоненти + пропрієтарні в **окремому встановлюваному модулі**. Розділення стає не
«відріж код», а «які плагіни в переліку» — пропрієтарний модуль просто не включають.

---

## Вердикт відповідності: 0 / 3 шари

| Шар | Стан зараз | Відповідність |
|---|---|---|
| SDK / адаптери | `from . import pyarrow_, pydantic_, glue` — фіксований набір | ❌ статичний, не реєстр |
| Бекенд / console_api | плоский `ROUTES` dict + `from routes import (...)` + `ROUTES.get()` | ❌ моноліт, нуль самореєстрації |
| Фронт / UI | Next.js файлові сторінки + прямі імпорти + сайдбар з даних | ❌ нема точок розширення |
| Механізм плагінів | — | ❌ нема ніде (ні entry_points, ні реєстру) |

Усе зшито статично. Щоб «легко маніпулювати що куди» — спершу треба ввести реєстр і
перевести захардкоджене зшивання на самореєстрацію. Зараз це greenfield.

---

## Що описує транскрипт (цільова модель)

1. **Скелет + реєстр + точки розширення.** Фреймворк сам по собі «голий», має точки
   розширення (раути, сайдбар, навігація). Компоненти вставляють у них свої частинки.
2. **Самореєстрація на імпорті.** Імпорт модуля-компонента реєструє його раути / пункти
   меню / в'юшки в спільному реєстрі.
3. **Explicit перелік плагінів** (Мирослав надає перевагу явному над неявним обходом):
   перелік модулів із пріоритетами; система ініціалізує по черзі, кожен реєструє своє.
   Неявний варіант (обхід встановлених пакетів через entry_points) — теж робочий, але
   обрано explicit.
4. **OSS-компоненти + пропрієтарні в окремому модулі.** Фреймворк + OSS можна тримати
   разом (щоб не плодити репо), Enterprise — окремий встановлюваний модуль із контролем
   доступу.
5. **Багатство застосунку = що заімпортовано.** Опен-сорс білд = коротший перелік
   плагінів; пропрієтарний = довший (фреймворк + OSS + пропрієтарні плагіни).
6. **Іменовані адаптери** (named adapters) — кожен компонент має ім'я, адаптує/дореалізує
   підсистему. Це паттерн ZCA (Zope Component Architecture); аналоги є в стандартній
   бібліотеці (`importlib.metadata` entry points).

## Конверсія по шарах

### 1. Бекенд (console_api) — реєстр раутів. *Найважливіше, середній обсяг.*

Зараз: `main.py` тримає літеральний `ROUTES = {(method, path): (handler, param), ...}` і
статично імпортує всі хендлери з `routes`.

Стає:
- Реєстр замість літерала. Декоратор на кожному хендлері:
  ```python
  @route("GET", "/api/pipelines")              # param=None
  def list_pipelines(event): ...
  @route("GET", "/api/pipeline-status", param="name")
  def get_pipeline_status(name, event): ...
  ```
  Імпорт модуля → декоратор вставляє запис у спільний реєстр.
- `main.py` стає **ранером**: явний перелік модулів-плагінів, далі диспетч із реєстру.
  ```python
  # explicit plugin list — OSS build:
  import routes.health, routes.pipelines_list, routes.pipelines_info, ...
  # proprietary build additionally:  import ee.team.api_routes...  (окремий модуль)
  route = REGISTRY.get((method, path))
  ```
- Розділення: OSS-перелік = безкоштовні route-модулі; пропрієтарний перелік (в окремому
  `ee`-модулі) додає Team/Enterprise route-модулі. Лямбда=ранер, плагіни додають раути.

Сигнатури вже сумісні: `(handler, param_key)` тривіально лягає в декоратор. ~14 route-
модулів перевести на `@route`, `main.py` — на ранер.

### 2. Фронт (UI) — точки розширення для раутів/сайдбара/навігації. *Найбільший обсяг.*

Зараз: сторінки = файли (`app/assets/page.tsx`...), навігація захардкоджена, нема куди
плагіну вставити «вкладку Assets».

Стає:
- Реєстри: `routeRegistry`, `navRegistry`, `sidebarRegistry`. Кожен feature-модуль
  реєструє свою сторінку + пункт навігації.
- Шелл рендериться з реєстрів, не з захардкоджених сторінок/навігації.
- **Explicit маніфест** перелічує feature-модулі для завантаження. OSS білд вантажить
  безкоштовні фічі; пропрієтарний — безкоштовні + пропрієтарні (з окремого `ee`-UI-модуля).
- Складність: Next.js файлова маршрутизація суперечить реєстру. Або перехід на
  реєстро-кероване роутування, або лишити файли, але показ/реєстрацію гейтити маніфестом.
  Це найдорожча частина — семи нема взагалі.

### 3. SDK адаптери — іменований реєстр. *Дрібно, не на межі тарифів.*

Зараз: `from . import pyarrow_, pydantic_, glue` (фіксовано).

Стає: реєстр, де кожен адаптер реєструється під іменем:
```python
@adapter("glue")
class GlueAdapter: ...
```
а `Asset.from_*` / резолвер шукають за іменем. Робить адаптери підключуваними (пропрієтарний
адаптер реєструється без знання ядра). Адаптери — не межа OSS/платне, тож це «вирівняти
під патерн», а не «треба для розділення».

## Чому ця модель і дає те, що ти хочеш

Після конверсії розділення = **explicit перелік плагінів**, не хірургія:
- OSS репо/пакет = скелет + OSS-плагіни (разом, щоб не плодити репо).
- Пропрієтарне = окремий встановлюваний модуль, доступ під контролем.
- «Перелік того, що йде в реліз» = перелік імпортів плагінів. OSS-білд перелічує OSS-
  плагіни; пропрієтарний додає пропрієтарні.
- Нічого не «вирізаєш» — просто не включаєш пропрієтарний модуль. Фреймворк вантажить ті
  плагіни, що в переліку.

Перенести фічу між тарифами = перенести її плагін-модуль між OSS- і пропрієтарним
переліком. Ось воно — «легко маніпулювати що куди».

## Обсяг і порядок

| Крок | Шар | Обсяг |
|---|---|---|
| 1 | Реєстр раутів console_api (декоратор + ранер + перевести 14 модулів) | середній |
| 2 | Реєстр адаптерів SDK (опційно, вирівняти патерн) | малий |
| 3 | Точки розширення UI (реєстри раутів/нав/сайдбар + маніфест + роутинг) | великий |

Бекенд — перший і найвищий ROI (моноліт `ROUTES` найжорсткіший, конверсія чітка).
UI — найважче, лишити наостанок. Жодного з цього в коді зараз нема.

> Це замінює попередній підхід «вирізати підмножину» (publish-машинерія + `ee/`-strip).
> Тут розділення вбудоване в архітектуру, а не накладається зверху скриптом.
