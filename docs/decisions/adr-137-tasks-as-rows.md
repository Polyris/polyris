## Context

ADR #130 made readiness a decision taken in one place, from facts, with hints that may be lost and a sweeper that checks again. That layer carries over. The defects the 1.2 reviews and the release rehearsal kept finding came from the layer under it: every task was a live `dependency_wrapper` execution for its whole run, waiting on single-use tokens. A task row had many writers (the wrapper, registration, `run_task`, the pause wait, the failure handler, the restart helper, the console, the reconciler); every task held a token of its run, and six places had to answer it (ADR #135); a `waiting` row meant "a live process somewhere", checkable only through a lagging `DescribeExecution`; a pause parked a `run_task` execution on a token; a restart stopped two executions and started a third; executions ran for days on an old definition; status, output, facts and the run's answer were separate states with separate catches.

Principle #42 triggered: the class "a process ended and told no one" kept recurring (a run left `RUNNING` after a timed-out wait, among others), and each fix added a rule every writer had to follow. This ADR changes the model.

## Decision

### 1. The model

A waiting task is a row in the tasks table (`pipeline-tokens`) and nothing else: no execution, no token. An execution exists only while the task's work runs. Each run has one row of its own, the run row, which holds the run's only token.

```text
pipeline --> Start_Run: writes the run row (creating, with the run's token),
             the run's input and every task row (waiting), then marks the run active

the run turns active  --> tasks-table stream  ---\
extract's row changes --> tasks-table stream  ---+--> dispatcher: a pass over the run, decide(load)
a fact is recorded    --> asset-events stream ---+      ready --> writes deps_ready --> starts run_task(load)
the sweeper, as a net ---------------------------/
```

- **`Start_Run` writes the run.** The generated state machine keeps its registration chain (`Register_Pipeline`, the asset subscriptions, §8), then runs `Start_Run`, a `lambda:invoke.waitForTaskToken` state in a `Parallel` beside the direct steps.
  - **Specs come from a table.** `polyris-deploy` writes every task's spec to `pipeline-specs` before it changes the stack; the state's arguments carry only a reference (§8). `Start_Run` reads and checks the specs, writes on each task row only the fields the dispatcher decides on plus the hash of the spec text, and on the run row the `spec_id` (§3). The dispatcher, Restart and Mark Successful never read the registry.
  - **The run's input is an item of its own**, written once (§3): `variables`, `skip_tasks`, the flags that set the cascade of its facts (ADR #57) and its `PARTITION_ARG`. `triggered_by` stays on the run row. Task rows keep no copy, apart from the few fields the console reads on them (§3).
  - **The format comes with it.** The arguments carry the pipeline's format version; `Start_Run` checks it before anything else, stamps it on the run row and refuses one it does not support, with the cause (*Migration and upgrade*).
  - **The run row first, active last.** `Start_Run` writes the run row `creating` with its token, by update (never put, so a direct step's earlier mark survives). Then the run's input, one row per task (`waiting`, or `skipped` with `skip_origin = run` for a task in the run's `skip_tasks`), then the `asset:{name}` pointers of the tasks with `wait_for`, and last it marks the run row `active` unless it carries the stop mark (§4). `skip_tasks` is the only list it reads (ADR #60); it never reads `skip_on_backfill`: whoever starts a run names the tasks to skip. Nothing starts for a run whose run row is missing or still `creating`, so a `Start_Run` that fails half-way starts no task.
  - **Conditional writes.** Each row is a conditional put (a batch write takes no condition), and `Start_Run`'s timeout fits the largest pipeline `polyris-deploy` accepts (§8). Every row carries the execution's name and `StartTime`; an existing row is accepted only with this execution's name and `StartTime`, so a retry or redrive writes nothing twice, and a row of another run fails `Start_Run` with the cause. A pass or a stop acts only on the rows of its own run.
  - **One token per run.** Each attempt of `Start_Run` brings a new token. The run row keeps the latest attempt's, ordered by `Execution.RedriveCount`, then `State.RetryCount` (§9); `State.EnteredTime` is the same for every retry, so only the counters order tokens. A later token replaces the stored one, clears its answered mark and raises `run_version` (§3); an earlier one never replaces a later one (Step Functions refuses it with `TaskTimedOut`), and neither moves the run row back to `creating`. The stop mark refuses both a new token and the activation, so an attempt after the engine stopped the run fails into the `Catch`, with a warning (§4).
  - **It returns once the run is active.** The activation wakes the dispatcher through the stream (§7); its first pass starts the root tasks, and answers the token at once when every row is already final (every task skipped).
  - **A redrive** that runs `Start_Run` again finds the rows in place and writes none twice; its newer token makes the run row due at once, and the sweeper answers it from the rows within 5 minutes. A redrive of a failed run runs no `Start_Run` (the execution fails after the `Parallel`, so it fails again at once); Restart is the way to run a failed run's tasks again. A redrive of an aborted run runs `Start_Run` with `RedriveCount` 1 and `RetryCount` 0, so the order stays.
  - **Retry.** `Start_Run`'s `Retry` treats `Lambda.TooManyRequestsException`, `Sandbox.Timedout`, `Lambda.Unknown` and HTTP 5xx as transient (Principle #53), and no entry matches the error name with which the dispatcher answers a failed run (§9). Its timeout and retry window derive from the maximum number of tasks per pipeline (§8). The sweeper waits for a run row still `creating` as long as the whole `Retry` envelope. One parity test pins that window, the template timeouts of `Start_Run` and the dispatcher, and the pass budgets below them (Principle #28).
  - **Catch.** A `Start_Run` that fails for good starts no task; its `Catch` writes a `coordination` warning with the run and the cause (built like every warning row of the generated state machine), the branch records the error as a direct step's branch does, and the pipeline fails after the `Parallel` (a failure inside it would cancel running direct steps). This covers retries used up, a refused format, specs missing or not matching their fingerprint (§8), rows of another run, an input over 256 KB, and an attempt that finds the stop mark. The `Catch` also names `States.DataLimitExceeded`, which AWS documents as outside `States.ALL` (a `Catch` on `States.ALL` took it all the same, *Probed AWS behaviour* B2). The dispatcher's answer of a failed run is not such a failure: a `Catch` ahead of it takes that answer by its error name, and the branch records it without a warning.
- **One dispatcher decides and acts.** The `reconcile` function of ADR #130 becomes the dispatcher, under the same logical IDs and names (*Migration and upgrade*). Its one entry point is a pass over a set of a run's rows (§7): the stream and the sweeper pass over all of them, AssetFanout over the rows that wait for a new fact. A pass reads the run row and its set once, consistently, decides each waiting row with `decide`, and writes: `ready` → `deps_ready`, then starts `run_task`; `skip` or `upstream_failed` → that status; `paused` → `waiting_paused`; `wait` → the reasons and the next deadline with the decision's time, only when they differ from those the row holds (the reasons hold no time, so a pass where nothing changed writes nothing).
  - Each decision that moves a row is one transaction of two items: the row's write, conditional on the status and generation the pass read, and a `ConditionCheck` on the run row's `run_version` as read. Every write that can make such a decision wrong raises `run_version` in its own transaction (§3): an operator's action, a reset of a Restart with dependants, a new token, a Pause or a Resume, every request, the stop mark included. So no decision stands on a read taken before such a write; the same check keeps `deps_ready` out of a run a Pause (§5) or Stop (§4) reached after the read, and a pass that read the run paused or being stopped writes no `deps_ready`. A refused transaction is decided again from a new read of the run row, the row and its direct upstreams, within the pass's budget.
  - Last, a full pass decides the run's end and writes the run's summary when it changed (§4). It signals no token: no task holds one.
  - **It owns `wait_before`.** A ready task with a countdown stays `waiting` until `enabled_at + wait_before` (`trigger_rules.enabled_at`); the row records the countdown's end as its due time and the console's countdown, and no pass decides it before then. At the end a pass decides it again from its upstreams without judging a `.within()` condition again, so an upstream restarted during the countdown holds it; a pause holds it too (§5).
  - **It reads a task's spec when it starts the task**: one `GetItem` on `pipeline-specs` by the hash on the row; with the run's input item (read once per pass that starts tasks) it builds `run_task`'s input in Python (§9). A text never changes, so a restart runs the same spec.
  - **It passes on the upstreams' statuses**, with their skip origins, as the pass read them.
  - **A start that keeps failing.** A transient error leaves the row `deps_ready`, due again after a backoff of up to 5 minutes; the row records its first and latest failed attempts, from which the due-time function gives the next try. After 15 minutes of failures it writes one `coordination` warning; after 6 hours it fails the row with the last error (§5).
  - **It writes the timeline.** `DEPS_READY`, `DEPS_SKIPPED` and `DEPS_BLOCKED` follow the status, best effort. A row's `task_run_id` is the name of its `run_task` execution (invariant 4), so each generation has a timeline of its own. A task that fails without `run_task` recording it (`fail_wait`, `fail_start`, `fail_dead`) ends its timeline with `TASK_FINISHED` `failed` and the cause.
- **Each pass judges a row from the row itself.** The deadline and due-time functions are pure (§9): they read the row, its upstreams and the run row, never the row's stored due time. So a pass acts on each row of its set whose time has come: it fails a row past its limit or decision deadline, decides again a row whose countdown ended, and starts again a `deps_ready` row whose next try has come unless the run is paused or being stopped (§5).
  - **Execution checks.** Only the sweeper's passes, and the pass an execution's end wakes (§7), judge the execution of a `deps_ready` or `running` row whose liveness check has come; the stream's passes and narrow passes make no `DescribeExecution` call. A pass an execution's end wakes makes at most two: the run's execution or one row's `run_task`, and once more after a refused write; it comes only on an `ABORTED`, `TIMED_OUT` or `FAILED` end (a failed run's ordinary end included), never the engine's own stop, and the fenced write lets one of it and the sweeper through. A sweep makes at most 200 such calls (`sweep.DESCRIBES`), below the API's bucket of 250–300; a row past them stays due. Each run's own execution takes its call first; rows take at most a quarter of the calls (150 a sweep), the longest due first (`sweep.grant`), so one large run never holds back the others. Above about 900 long-running tasks in the account their checks come less often than every 30 minutes.
  - A narrow pass judges only the rows of its set, not the upstreams it reads. Each pass compares the stored due time of each row of its set with the due-time function and writes the difference. A removal or postponement that a pause causes carries the same `ConditionCheck` on `run_version`, so a Resume after the read keeps the due time (§5). Any other race costs one extra check or a due time missing until the next full pass, at the latest the run row's check within 30 minutes (invariant 9): a row's own due time only makes its check punctual.
- **The console shows why a task waits**: the reasons and deadline the dispatcher recorded, with their time, and each upstream's verdict, computed with `trigger_rules.evaluate` from the rows it loads. No route is added. This replaces what the Step Functions console showed (ADR #20).
- **`run_task` only runs the work.** Its first state moves the row from `deps_ready` to `running` under the generation it was started with, counting the row's starts in `attempt` and keeping `status_since` (so the liveness check stays where the start put it). A claim whose answer was lost finds its own claim (generation and execution) and goes on; any other refusal ends it quietly; a claim that cannot be written ends the execution with the cause, and the dispatcher fails the row at its liveness check. Every DynamoDB call of `run_task` is retried for about two minutes on any error but an answer (a failed condition, a cancelled transaction, an expression error, a payload too large) (`test_every_dynamodb_state_retries_any_error_but_an_answer_for_minutes`). It no longer checks the pause, waits for a decision, notifies dependants or answers the run.
  - **What it reads from its upstreams.** An upstream's output from `output#` only when that upstream succeeded or an operator or the run skipped it. A succeeded upstream has an `output#` item, written with its success; when it is missing, `run_task` fails the task with that cause (1.2 started the work without it). Outputs are read consistently. Any other upstream reaches the task as its status alone, so a task never reads an older run's output of the same date: not after a failure, and not beside an upstream that still waits or runs when a `one_success` or `one_failed` task starts.
    - An output reaches the task inline up to 25 KB while all of them fit a budget shared with the input, otherwise as a marker that `xcom` reads from `output#`; below a share of 64 characters only the status reaches it; an output over 256 KB (which `xcom.push` may write) is a marker. A string result that starts like JSON is JSON text (`json.dumps`), stored as is and read parsed; any other string is stored as a JSON string (`"ok"`), and one an older version stored as is reaches the task as that string (`test_a_result_is_stored_as_json_text_as_1_2_read_it`).
    - The statuses reach the task in the event's `upstream` entries, for ECS and Batch in `POLYRIS_UPSTREAM_STATUSES` beside `POLYRIS_TASK_NAME`, and for Glue in the job argument of that name (§9). Through `xcom` (`get`, `pull`), reading an upstream that failed finally raises `XComUpstreamFailedError`, and any other upstream without an output in this run `XComMissingError`; a test keeps the set `xcom` reads equal to the one `run_task` reads (`test_the_set_run_task_reads_is_the_set_xcom_reads`).
    - An EMR step gets no environment variables (ADR #123), so no statuses: after a failed upstream `xcom` can give it an older run's output of the same date, a documented limitation; `run_task` adds nothing to the step's arguments.
  - **The work's time limit.** `execution_timeout` is the `TimeoutSeconds` of the work states, per attempt. A timeout is a failed attempt: the task's retries, then the decision of ADR #114. The work states never retry `States.Timeout` themselves (a test pins it). A timeout ends the state, not always the work (a Lambda runs on to its own timeout; a `.sync` job is stopped within 15 to 60 seconds), so a retry after a timeout waits at least 60 seconds and two copies of the work do not overlap.
  - A task that fails after its retries is written `waiting_decision`, with the time it began to wait and the decision timeout in force, and `run_task` ends; its `attention-index` entry falls due at the deadline (§6). No process waits for the decision (§5).
  - **One transaction on success** writes the status, the output and the asset facts. The output is stored once, in `output#` (what `xcom.pull()` and the console read); the task row keeps no `result`. A dependant never starts before the data it reads (invariant 12), and a success without its facts cannot happen. A transaction holds at most 100 items, so a task has at most 97 outlets, which `polyris-deploy` enforces (§8): Mark Successful writes the run row too.
  - After `DynamoDb.TransactionCanceledException`, or any error whose write may have applied, `run_task` reads the row: its own success under its generation is a retry after a lost answer and it stops; a raised generation ends it quietly (Rule 47); any other cause sends the transaction again with a new time for the conflicting fact. `Record_Success` runs at most five times, each with short retries. A success that still cannot be recorded makes the row `waiting_decision` with the cause, and the work runs again only if an operator restarts it. Its `Catch` names `States.DataLimitExceeded` and the SDK integration's errors (`DynamoDb.*`, not the optimised `DynamoDB.*`); its `Retry` names only what it does not retry. A work result over 256 KB fails the work state before any transaction: a large value takes the claim-check pattern of `DATA_PASSING.md`.
  - `run_task` keeps the calls to `NotifyFunction`: when a task fails, and after a success of a later start (`attempt > 1`).
- **The dispatcher answers the run** once every row is final (§4). No other code answers a run's token.
- **Direct steps stay, and their failures wait for the rows.** Steps without dependencies (`wait`, `pass`, `sns`, `sqs`, `s3` and the like) remain branches of the `Parallel`. A failed one is caught in its branch, which records the error and writes a `step` warning (a `WarningKind`). In a pipeline with tasks the branch also marks the failure on the run row; the mark carries the execution's name and `StartTime`, so it and `Start_Run`'s writes accept each other in either order (a mark first makes a run row with no status, token or `start_day`, which nothing acts on until `Start_Run` completes it).
  - The mark writes the history TTL when the row has none (§5), and its `Retry` covers throttling and a conflict with a transaction that checks the run row (§7). A pipeline without tasks has no `Start_Run` and no run row (§8). After the `Parallel`, the pipeline fails its execution when a branch recorded an error, so it ends only once every branch has; `Start_Run` ends only when its token is answered, so the run's tasks finish first.
- **Wrapper steps become rows.** The `lambda`, `glue`, `ecs` and `athena` steps become rows like tasks, with a task's defaults (§5); their classes have no time-limit field, so the 1 hour of a `lambda` step and the 24 hours of the others go with the other 24-hour defaults.
- **Steps without a generator leave the DSL.** `Choice`, `Map`, `Sensor`, `ShortCircuit` and `Condition` had no generator; they are deleted (a `dag.py` that imports one gets an `ImportError`), and a test fails for any exported step without one.
- **The wrapper goes.** `dependency_wrapper` and its helpers are deleted, with no adapter and no stub (*What is removed*). `run_task`, `bulk_backfill` and the three test state machines remain.

### 2. Invariants

Each invariant has a test in the coordination harness (*Tests*).

1. **A task that does not run has no execution and no token.** Its state is its row alone, a countdown of `wait_before` included.
2. **Apart from an operator's action, only the dispatcher moves a row out of `waiting` or `waiting_paused`,** with a write conditional on the status and generation it read and on the run row's `run_version` as read (§1).
3. **Write first, then start.** A row becomes `deps_ready` before its `StartExecution`, and a pass starts a `deps_ready` row again once its next try has come, unless the run is paused or being stopped. ADR #130 rejected a sender that writes the status because a crash between signal and write lost the status and a consumed token could not be told from an expired one; with no token and a start safe to repeat, neither applies.
4. **At most one `run_task` per row and generation.** The execution's name is a prefix of the row key plus a hash of the key, the run's `StartTime` and the generation, within the 80 characters Step Functions allows. `ExecutionAlreadyExists` counts as done. With the start time in the hash, a run name used again after its old rows expired cannot meet an old `run_task` name (§5).
5. **`run_task` writes only under its own generation.** A refused write ends it quietly (Rule 47).
6. **An action that ends a task's ownership is one transaction that raises the generation:** an operator's action, the dispatcher's work on a request, and the engine's stop of a run (§3, §4). Stopping an execution afterwards is cleanup only: the raised generation already fences it.
7. **One pure table in `polyris/coordination/` allows each transition** (§3, Principle #48). It gives, for each status, the row's kind in `attention-index` (§6), and for each transition whether it wakes the dispatcher (§7). Every write of a row takes its condition from that table and its due time from the due-time function (§9). `tests/sdk/test_task_row_writers.py` checks every writer against both, and every writer of the run row against whether it raises `run_version` (§3).
8. **A run's end is decided from facts.** When every row is final, the current token is answered and the run row records which token was. A closed token means it was answered already or its execution ended. No token is answered and no execution ends while a row is not final, outside the stop paths of §4. A Restart that lands after a pass read every row final, or after the run's end, makes a row unfinished after the answer: the run then runs as after its end (§3), and no second answer comes.
9. **Every unfinished row is covered by its run row's due time in `attention-index`.** The run row is due, at most 30 minutes apart, while its run has an unfinished row, a stop in progress or a request, and until its answer is recorded (§3). Each check is a full pass that judges every row from the row itself (§1), so a row needs no due time of its own to reach its limit, deadline or next check.
   - A row with a time of its own (a wait limit outside a pause, a countdown, a decision deadline, a start to retry, a `run_task` whose liveness is judged) also has its own due time, which makes that check punctual.
   - Every pass writes its rows' due times as the due-time function gives them, so the run row's check puts back a lost one within 30 minutes.
   - A row that waits only for other rows or for a Resume is woken by their changes, and its run row's check finds a lost hint.

   This replaces ADR #130 invariant 5, which put every waiting row in the index.
10. **No fail-open.** No read failure, partial result or unknown state leads to a start, a close or a run's answer. An execution that `DescribeExecution` does not show yet is not a dead one (`sweep.EXECUTION_VISIBLE_AFTER`).
11. **A row outlives its run.** No row a run writes expires before the run ends: task rows, `output#` rows, pointers, the run row and its input (§5). Timeline events and `input#` are not such rows: only the console reads them.
    - When a row of an active run is missing all the same, the dispatcher fails each waiting dependant with the cause, counts the row as failed for the run's end, and writes a `coordination` warning.
    - A task row whose run row is missing is stopped, with the cause, by the first check or pass that reads it: the sweeper's check of a row with its own due time, or a pass that a change of another row starts; a row a 1.2 run left in flight is skipped (*Migration and upgrade*). With no run row no spec version names the rows, so that pass finds them in `pipeline-execution-index` and stops each after a consistent read by key; a row the index does not show yet is stopped later. Rows of a run whose run row was deleted by hand while they waited on a lost hint or a pause stay until their TTL.
12. **No status is visible before the data its dependants read.** A status write is the wake-up (§7), so `run_task` and every operator action that ends a task write the status in the same transaction as the output, the output marker and the asset facts.

### 3. Who writes which transition

This section is the table of invariant 7. *Final* means a status in `SETTLED_STATUSES` (`transitions.FINAL`): `TERMINAL_STATUSES` and `stopped`, that is `success`, `skipped`, `failed`, `upstream_failed`, `stopped`, and `succeeded` and `aborted` on rows written before 1.3. *Wakes* says whether a transition wakes the dispatcher through the stream (§7). *Attention* is the row's entry in `attention-index` after the write (§6); a due time is an entry of the `waiting` kind, which a row has only for a time of its own (invariant 9).

**Task rows.**

| From | To | Writer | Wakes | Attention |
|---|---|---|---|---|
| no row | `waiting`, or `skipped` with `skip_origin = run` for a task in the run's `skip_tasks` | `Start_Run` | no | its due time, if it has one |
| `waiting` | `waiting_paused`, and back | the dispatcher | no | none in `waiting_paused` |
| `waiting`, `waiting_paused` | `deps_ready`, before it starts `run_task` | the dispatcher | no | due at its next start or check |
| `waiting`, `waiting_paused` | `skipped` with `skip_origin = rule`, or `upstream_failed` | the dispatcher | yes | none |
| `waiting`, `waiting_paused` | `failed`: at the wait limit, on a `CoordinationError`, or when a dependency's row is missing | the dispatcher; the sweeper finds the limit | yes | `failed` |
| `deps_ready` | `failed`, when the start is refused for good (an input over 256 KB) or keeps failing past its deadline (§5) | the dispatcher | yes | `failed` |
| `deps_ready` | `running`, then `success` or `waiting_decision` | `run_task`, under its generation | for `success` and `waiting_decision` | due at its next check while `running`; none on `success`; `decision` at its deadline |
| `deps_ready`, `running` | `failed`, when the execution of the row's current generation ended without an outcome | the dispatcher, through `DescribeExecution` at the sweeper's check of the row, or at once when the end comes on EventBridge (§7) | yes | `failed` |
| `waiting_decision` | `failed`, at the decision timeout | the dispatcher; the sweeper finds the deadline | yes | `failed` |
| any status but `success` and `skipped` | `skipped` with `skip_origin = manual`, or `success` | the console: Skip, Mark Successful | yes | none |
| a status that is not final | `failed` | the console: Fail | yes | `failed` |
| a status that is not final | `stopped` | the console: Stop; the dispatcher: a Stop of a run (§4), and a row whose run row is missing | yes | none |
| a final status, or `waiting_decision` | `waiting` | the console: Restart; the dispatcher: the dependants of a Restart with dependants | yes | its due time, if it has one |

Every write by the console raises the generation, and so does every write the dispatcher makes for a request or a stop. Every operator action also raises the run row's `run_version` in its transaction. Nothing writes `aborted` any more: every Stop writes `stopped`, a waiting task's included.

**The run row.**

| From | To | Writer | `run_version` | Wakes |
|---|---|---|---|---|
| no row, or a direct step's mark alone | `creating`, with the attempt's token | `Start_Run` | raised | no |
| no row, `creating`, `active` | the same, with the mark of a failed direct step | the step's branch (§1) | kept | no |
| `creating` | `active`, after the last task row, unless the stop mark is set | `Start_Run` | raised | yes |
| `creating`, `active` | the same status with a newer token, which clears the answered mark, unless the stop mark is set | a later attempt of `Start_Run`, or a redrive | raised | no |
| `creating`, `active` | the same status with the stop mark, which starts a stop of the run | the console: Stop of a run, while `active`; the dispatcher, for a run whose execution ended before its answer or that never became active (§4) | raised | yes |
| `active` | the same status with a request, the run row's long TTL and its due time (the request is the asset pointers of the rows it puts back to wait, and for Restart with dependants the reset of the dependants) | the console: Restart, Restart with dependants (§5) | raised | yes |
| `active` | the same status, due at once when it has no due time | the console: Skip, Fail, Mark Successful and Stop of a task, in the action's transaction, also of a row already final | raised | no: the task row's change wakes |
| `active` | the same status | the dispatcher: each reset of a Restart with dependants | raised | no |
| `active` | the same status with the pause opened or closed | the console: Pause, Resume | raised | yes |
| `active` | the same status with a request cleared | the dispatcher, once it has carried the request out | raised | no |
| `creating`, `active` | the same status with its token answered and marked | the dispatcher, once every row is final (§4), or once it has stopped the rows of a run that never became active | raised | no |
| `creating`, `active` | the same status with the stop done | the dispatcher, once every row is final and the run's answer is marked (§4) | raised | no |

No transition leads back to `creating`.
- **`run_version`** is raised by every write in the table except the mark of a failed direct step, and by nothing else; the writes of the run row's due time, summary and TTL keep it, since none can make a decision wrong. A pass's decisions check it and never raise it (§1). A pass raises it only by a write of the table (a reset, its stop mark, the answered mark, the stop done, a request cleared), each conditional on `run_version = :read` and setting `:read + 1`, except the answered mark (§4): that one is conditional on its token being current and not yet marked, and raises `run_version` whatever it is, so a Restart between the pass's read and its answer runs as one after the run's end instead of the engine stopping the run for an answer it never saw marked. When the condition fails, an action, token or request came in between: the pass reads the run row and its rows again and decides again.
- A pass that changes the run's summary writes it (§4), a write that wakes nothing.

**The run row's due time** is the safety check of its run's rows (invariant 9), and each check is a full pass (§7).
- `Start_Run` sets it. A request makes it due at once, and so does a pass that leaves rows for its budget or a conflict, which also sets the run row's `left_at` (§7). "Due at once" always writes the current time, a new value, so a move by the sweeper that read the old one fails.
- A Restart sets it again in its transaction, also after the run's end; Skip, Fail, Mark Successful and Stop of a task make it due at once when it has none. So after the run's end a lost stream record cannot leave the summary stale (§4).
- It stays while any row is unfinished, a stop is in progress or a request waits. After each check the sweeper moves it on by the backoff, at most 30 minutes, and clears `left_at`; after a check whose pass failed it also writes a `coordination` warning (§7), and a pass that failed for good marks the run row (`check_failed`), which a later passing check clears. A run whose pass failed for good waits for its run row's backoff, not every sweep (`test_a_broken_run_waits_for_its_backoff_not_every_sweep`).
- Each move is conditional on the due time and `run_version` the sweeper read, so it never postpones a check a request, pass or action set meanwhile.
- A pass removes it only once every row is final, no stop is in progress, no request waits and the answer is marked, conditional on the `run_version` it read. A run that never became active is closed the same way.

**The run row's contract.** Its fields are named constants in `polyris/coordination/` (§9).
- **Key.** `_run_` followed by the run's `pipeline_execution`. It starts with `_`, so `is_internal_record` skips it and every console loop over task rows skips it through `should_skip_token_row`.
- **Indexes.** It carries no `date`, `pipeline_execution` or `backfill_id`, so it is in neither date index. Only `start_day` puts it in `run-start-index` (§5), and its due time in `attention-index` while it is due.
- **Fields.** `status`; the current token, its attempt order and the answered mark; the stop mark and whether the stop is done; `run_version`; `left_at`; the execution's name, `StartTime` and ARN, which the engine's check describes, so it reads no registry (§4); `pipeline_name`, the run's date as `run_date`, `start_day`, `started_at`, and `finished_at` with the answer; `triggered_by`; `spec_id`, `task_count` and the format version; the summary; the mark of a failed direct step; the requests; the pause intervals; the sweeper's count of checks and the mark of a failed one; the TTL.
- **Size.** Every decision's transaction checks the run row and DynamoDB bills the whole item, so the row stays under 5 KB (a task token alone takes up to 2,048 characters). The answered mark is the token's order, not the token. It keeps at most ten pause intervals; a Pause past ten merges the two oldest, which can only move a deadline later. A Stop's reason is capped at 500 bytes of UTF-8, and the other free-text fields at their own caps (`run_row.py`); a test builds the largest row the code can write.
- **No task names.** A pass takes them from the run's spec version (the dispatcher keeps the names of each `spec_id` it read). A spec version read with fewer items than `task_count` is a read failure (invariant 10).
- **The run's input** is an item of its own, keyed `_run_{pipeline_execution}#input`, holding the run's `variables`, `skip_tasks`, cascade and `partition_arg`; it enters no index. `Start_Run` writes it once (§1). The dispatcher reads it to build `run_task`'s input, Mark Successful for the cascade flags, the console for what it shows.

**Fields that stay on task rows for the console.** Besides its status, its times and the readiness fields (§8): `triggered_by` (the feeds and History tabs), `attempt` and `retry_attempt` (ADR #125), `restarts` (the operator's Restarts, shown as ↻), `parent_execution_id`, `task_type`, `task_run_id`, `backfill_id` (the key of `backfill-id-index`) and `task_date`, the run's date again, since `attention-index` projects that field for the bell and not `date` (§6).

**Operator actions.** Every operator action goes through one pure builder in `polyris/coordination/` (`actions.py`, on the task-row write the dispatcher shares, `row_write.py`): Skip, Fail, Mark Successful, Stop, Restart, Restart with dependants, Stop of a run, Pause and Resume. It builds the transactions from the rows its caller read. The console sends the light ones; the dispatcher sends those of the heavy ones and of its own stop of a run (§4). Pause and Resume update the run row's pause state; only the dispatcher moves rows between `waiting` and `waiting_paused`.
- An action that ends a task is one transaction (invariants 6 and 12): the status, conditional on the status and generation read, a raised generation, the output marker that dependants and the console read, for Mark Successful the asset facts of the outlets in the task's spec, and for Skip `skip_origin = manual`.
- The same transaction raises the run row's `run_version` and makes the run row due when it has no due time, also for a Skip or Mark Successful of a row already final, so a pass that read the task before the action decides none of its dependants from that read (§1, ADR #138 §4).
- The marker's write carries its own condition, that `output#` is still as read (Principle #31). When the caller finds real output there, the marker stays out and a `manual` warning says so. A concurrent `xcom.push` cancels the transaction, and the caller builds it again from a new read. A transaction refused because a row's status moved is built again from a new read while the action still applies.
- A restart writes `waiting`, raises the generation and replaces the row's attention entry with its due time, if any (invariant 9); the same transaction raises `run_version`, writes the run row's long TTL and makes it due. So the old final status never serves a dependant and leaves the bell. It removes what the task's last run wrote on the row (`task_row.RUN_FIELDS`), so the row waits as `Start_Run` wrote it and its limits count anew; the attempt count stays. It also requests the row's `asset:{name}` pointers (no console transaction can hold them, since `wait_for` has no bound): the next full pass writes them before it decides any row, for the rows that wait since the request alone. A pending request keeps its first time (`if_not_exists`), so a second Restart before that pass loses no row of the first, and a pass under a Stop writes none and clears the request (`test_a_restart_writes_the_pointers_of_the_rows_it_put_back_to_wait_and_renews_nothing`).
- **Heavy actions are requests.** Stop of a run and Restart with dependants touch every row of a run: at about 25 ms per transaction, 2,000 rows take about 50 seconds, past API Gateway's 30, and a Stop that timed out would leave upstreams running. So the console writes the request on the run row, with who asked and when, and answers at once; the dispatcher carries it out in passes, within their budgets, through the same builder, and retries what failed. The UI shows the action in progress ("stopping…"); counts in run lists can lag by seconds. A request makes the run row due at once, so with the stream's consumer down the sweeper takes it within 5 minutes, and the System status shows the consumer's failure (§6). The console refuses a Restart with dependants while another reset or a Stop of the run is in progress, and a Stop of a run cancels a pending reset.
- **Restart with dependants** is `POST /api/task-restart` with `with_dependants`; it restarts the task at once, in the same transaction as its request.
  - Each pass that carries out the request builds the set to reset from its own reads: the descendants in the same run that are `upstream_failed` or that a rule skipped, and whose rule no longer gives that decision from their upstreams as they are now (rows being reset count as waiting). A dependant another final failure still blocks stays, once its other upstreams are final; one whose rule waits for an upstream that runs again is reset and decided again when that upstream ends. A skip by an operator or by the run stays.
  - A narrow pass over a run whose reset waits decides nothing: it leaves its rows to the full pass through `left_at` (§7), so no row is decided or started from an upstream the reset has not reached.
  - It resets one transaction per row, upstreams first, and writes the pointers of a reset row that waits for facts. Each reset raises `run_version` under the condition above, so a decision read before a reset loses its transaction (§1); an action between two resets makes the next fail, and the next pass builds its set again. Only a pass that resets nothing clears the request.
- Every action on a task is refused for a row that names no spec version (a row of a run from before 1.3, *Migration and upgrade*). A Restart is refused while a Stop of its run is in progress. Mark Successful is refused while the task's outlets cannot be read, since its facts belong to the success (invariant 12).
- A Restart counts itself in the row's `restarts`, from the count it read (`attempt` counts the task's runs, which missed a Restart of a task that never ran). A reset of a dependant counts nothing (`test_a_restart_counts_itself_from_the_count_it_read_and_a_reset_of_a_dependant_counts_nothing`).
- A Restart is refused once its run started more than a year ago less 90 days (`RESTART_TTL_MARGIN`), about nine months: nothing renews a run's rows, so the rerun has those 90 days to read what its run wrote (`output#` lives a year from its last write, the run's history a year and 90 days from each write, §5). An older date runs again instead. The window counts what the run wrote itself: an upstream's output the run skipped and the facts a `wait_for` waits on live a year from their own write, so a Restart within the window can find them gone; the upstream then comes without an output, and the wait runs to its limit. Renewing the history at each Restart would cost a write per row and per `output#` on every Restart of a run older than a day.
- An action on a task whose `run_task` is running stops that execution afterwards, as cleanup; a Lambda invocation runs on, but the raised generation fences its result. A stop that fails writes a `coordination` warning, as the dispatcher's does (§4): the work may run on.

### 4. How a run ends

- **A row is final** when its status is in `SETTLED_STATUSES` (§3); a row that waits for a decision is not final. One function answers "final" for the run's end, the trigger rules (ADR #138) and the console's run status.
- **A run has finished when every row is final.** The dispatcher checks it at the end of each full pass, from the rows it read. The outcome is ADR #112's `derive_execution_status`, which also takes the run row's mark of a failed direct step (§1). `success` answers the token with `SendTaskSuccess`; `failed` and `aborted` with `SendTaskFailure`, naming the failed tasks, capped so the cause stays within Step Functions' 32,768 characters (a longer cause fails the answer for good). The run row keeps no outcome of its own: the console derives the run's status from the rows, or from the run row's summary, and the mark.
- **The summary.** Each full pass counts the run's rows per status and writes the counts on the run row when they changed: a cache derived from facts, not counters accumulated from events (Principle #42). It writes them only when no pass that began reading later has written some, so a slow pass never replaces a newer count. The pass that finds every row final writes them on the `run_version` it read instead (no later pass comes to correct them, and no row leaves a final status without an action or a request, each of which raises `run_version`). With them it writes `finished_at`: the answer's mark writes the first end only, once per token, and a run that a Restart after its end finishes again ends anew. The run lists take each run's status from it with `derive_execution_status` (§5). Its counts lag the rows by seconds after a change that wakes the dispatcher (§3), and until the run row's next check (up to about 30 minutes) after one that does not, such as a start.
- **The answer is marked by token.** After the answer the run row records the token it answered, and leaves the attention index once no request waits on it (§3). The mark is conditional on its token being current and not yet marked, and raises `run_version` whatever it is; a newer token clears it (§1, §3), so a run whose token changed after an answer is answered again. If the answer does not get through: a closed token (`DEAD_TOKEN_CODES`) counts as answered; a transient error leaves the run row due and the sweeper repeats the answer; any other error writes a `coordination` warning and leaves the run row due (Principle #38).
- **A failure no longer ends the run at once.** A failed task first waits for a human decision (ADR #114). Once the failure is final, by Fail or by the decision timeout, the dispatcher decides its dependants by their trigger rules (ADR #138): one that needs the task to succeed becomes `upstream_failed`, an `all_done` one runs. Independent tasks run to completion, and the run fails only when every row is final, as in Airflow, Dagster and Prefect. There is no fail-fast option.
- **Stop is final for the run.** A stopped task's dependants are decided as after a failure (ADR #138), and the run ends when its other rows are final. A stopped row has no deadline. A Restart of the stopped task stays possible later, even after the run ended: alone it reruns that task; with dependants it also reruns those the stop decided.
- **The console's run status follows the same rule.** A run with a failed task shows `running`, with its number of failed tasks, until every row is final; both early branches of `derive_execution_status` return `failed` or `aborted` only then.
  - The run lists read run rows with their summaries (§5). A date filter still finds its runs through the task rows of its date; it reads the page's run rows in one `BatchGetItem` and takes a 1.3 run's status from its run row.
  - The console asks Step Functions nothing about a run. The engine keeps the run row true: a run whose execution ended before its answer is stopped when that end reaches the engine (§7), or at the run row's next check.
- **Stop of a run** writes the stop mark on the run row, with who asked and why, and is refused while the run row is `creating`. The mark starts a stop, a request in progress until every row is final and the answer is marked; the dispatcher then records the stop as done.
  - While the stop is in progress, the dispatcher makes a Stop's transaction for every unfinished row, in passes, dependants before their upstreams, so no pass sees a stopped upstream while a dependant still waits: `all_done` and `one_failed` rows are stopped too, and no clean-up starts after it.
  - No row becomes `deps_ready` during the stop: the mark raises `run_version`, which every `deps_ready` transaction checks (§1). A row that became `deps_ready` before the mark is stopped like the others.
  - A row whose status moved under its transaction is read again and stopped from its new status unless that one is final. A Stop of a run writes no output markers.
  - The dispatcher stops a stopped row's running `run_task` as cleanup, and once every row is final, the pipeline execution; it then answers the run, and the closed token counts as answered. A `run_task` that cannot be stopped writes a `coordination` warning (its work may run on; the fence keeps its result out of the row, the output and the facts). The engine's own stop (below) stops no execution: its execution has ended.
  - Once the stop is done, no pass stops a row again, and a Restart is accepted and reruns its task. The mark stays and refuses the run's activation and any new token (§1). A Stop after the stop is done starts a new stop (a new mark replaces the done one and wakes the dispatcher), and a Pause is refused only while a stop is in progress (`test_a_stop_after_a_done_stop_and_a_restart_stops_the_rerun`).
- **A run whose execution ended before its answer** is stopped the same way when that end reaches the engine (§7), or at the run row's next check: the dispatcher writes the stop mark with the cause, conditional on no stop mark (a Stop of the run also stops the execution before the answer is marked, and its mark keeps who asked and why). That covers an execution stopped in the AWS console, with the `bulk_backfill` execution that started it, or by `polyris-destroy`, and one that reached its year (§5). The dispatcher reads the execution's status through `DescribeExecution`. CloudFormation deletes a state machine only once its executions have ended, and a run keeps its execution open until every row is final, so `polyris-destroy` stops a pipeline's running executions until its stack is gone, and `polyris-down` the platform's own.
- **A run that never became active,** whose run row is still `creating` after `Start_Run`'s whole retry window (§1), is stopped the same way, with the execution's error as the cause; its execution's end does not stop it sooner. The mark keeps a late attempt of `Start_Run` from activating the run on top of the stopped rows. The dispatcher then answers the run's token, which closes the run row (§3).

### 5. Time limits, retention and pause

| What | Limit |
|---|---|
| One attempt of a task's work | none by default; `execution_timeout` sets one, and a timeout is a failed attempt: retries, then a decision (§1) |
| Waiting for tasks of the same run | none of its own: the wait ends with the task it waits for, which starts it or makes it `upstream_failed` |
| Waiting for `wait_for` facts | 7 days from when the task's own dependencies are met (`trigger_rules.enabled_at`); then the task fails |
| All waiting, when `orchestration_timeout` is set | capped by it; unset, it does not fall back to `execution_timeout`. `polyris-deploy` warns when it is under 7 days on a task with `wait_for` |
| A countdown (`wait_before`) | ends at the sweeper's first check after it, up to 5 minutes late |
| A start that keeps failing | one warning after 15 minutes, `failed` after 6 hours, from the first failed attempt (§1) |
| A decision on a failed task | the global decision timeout (`__global_settings__`, 5 hours by default, ADR #103) |
| A stopped task | none: Stop is final for its run (§4) |
| The run | one year, the longest a Standard execution runs |
| A run's history: task rows, run row, input, `wait_for` pointers | a year and 90 days from each write |
| A date's data: `output#`, operator markers included | a year from the last write |
| A task's input: `input#` | 90 days from each write |
| Timeline events (`task-events`) | 90 days from each write |
| Backfill records | as long as the backfill runs, and 90 days after it ends |

- **Precision.** A limit fires at the sweeper's check of the row, which falls due at the limit: up to 5 minutes late while the sweeper keeps up. A countdown ends the same way, and that check writes no lost-hint warning. Everything else runs on hints within seconds: a task that finishes, a fact that arrives, a resume, and an execution that ends without a write (stopped in the AWS console, timed out, or failed outside its catchers, §7). A lost hint, or a row's lost due time, costs at most the run row's next check, up to about 35 minutes. A lost stream hint also writes one lost-hint warning for its run (§7); a lost end of an execution writes none. The self-check reports the oldest overdue row, run rows included (§6).
- **The deadline function.** A row's next deadline is defined clause by clause here, so it is one pure function in `polyris/coordination/` with a test per clause (Principle #48, §9). Besides the limits in the table:
  - a Restart starts every limit of the row again;
  - `orchestration_timeout` covers the wait until the row is ready, not its countdown;
  - a ready row is not decided again during its countdown, so a `.within()` condition is not judged again when it ends;
  - an upstream's failure counts from when it became final, at the decision or its timeout, not from when its work failed;
  - the paused time inside a wait moves its deadline (below);
  - a `deps_ready` row whose start keeps failing warns at `START_WARN_AFTER` (15 minutes) and fails at `START_FAIL_AFTER` (6 hours), both from its first failed attempt: time counts, not attempts, so a short burst of throttling warns no one. Paused time moves both, and an `AccessDeniedException` counts toward neither (§7).
- **Retention.** A run writes rows with three lifetimes.
  - **Its history** (task rows, run row, input, `wait_for` pointers) gets a TTL of one year and 90 days at every write, longer than a run can live; nothing shortens it at the run's end, so a finished run's history stays about 15 months after its last write (*Alternatives*). The console shows the runs of 90 days; a date filter reaches any date whose rows remain, without the inputs after 90 days.
  - **A Restart renews nothing.** It writes the run row's own long TTL and requests the `wait_for` pointers of the rows it puts back to wait (§3); a reset writes its row's. A narrow pass that finds a row an operator's action finished deletes its pointers.
  - **A date's data** (`output#`, operator markers included) lives a year from the last write: every write renews it, instead of keeping the first TTL (`if_not_exists`), and no run's end resets it. So a rerun of any date of the past year that skips tasks still finds their outputs.
  - **A task's input** (`input#`: its upstreams' outputs and the run's variables at its start) is read only by the console (`routes/tasks.py`, `get_task_output`), never a rerun, so it lives 90 days from each write; kept a year it would be the largest part of the table's storage.
  - **Timeline events** live 90 days from each write, with no reset; a run longer than 90 days loses its earliest events. Invariant 11 does not cover them.
  - **Backfill records** get the long TTL while the backfill runs and 90 days once `bulk_backfill` writes their final status (a 30-day TTL at creation lost the record of a backfill longer than a month, and `bulk_backfill`'s `ADD completed_partitions` then created a record of the key alone, without a TTL).
  - **Unchanged:** asset facts 365 days, bell warnings 8 days, push retries 7 days, the results bucket 30 days. Push subscriptions and the registry have no TTL.
- **The table grows, so its scans go.** These lifetimes make the tasks table about ten times as large as in 1.2 at 1,000 tasks a day.
  - `/api/pipeline-status` and `/api/pipeline-dag` without a run query `pipeline-date-index` instead of scanning the table.
  - Every search of backfill records (`backfills_repo`) queries `pipeline-date-index` with `pipeline_name = _polyris_bulk_backfill` instead of scanning: the bell called `list_recent` every 30 seconds, and a scan of the grown table would outlast API Gateway's 30 seconds. Backfill records gain a `date`, the day they started, so they enter that index; it projects few of their fields (a change of projection would replace it), so the search reads the full records with `BatchGetItem`.
  - The `date` also puts them in `date-pipeline-index`. Every reader of the two date indexes skips them through `should_skip_token_row`, and a census test checks every read of those indexes. The bell no longer reads them (§6).
- **Run lists read run rows** from a sparse index of the tasks table, `run-start-index`.
  - **The index** holds run rows only. Its partition key is `start_day` (the `YYYY-MM-DD` of the execution's start, which only run rows carry), its sort key `started_at`. It projects what the lists show: `pipeline_name`, `run_date`, `status`, `finished_at`, `triggered_by`, the summary and the mark of a failed direct step, so a list reads no other item.
  - **The Runs tab** walks the start days newest first and stops once its page is full; stopping early is correct because the shard key is the day the run started, not its logical date. Its window is 90 days, and the Tasks tab's too.
  - **A pipeline filter** walks the same start days with a filter on `pipeline_name` until the page is full or the 90 days end.
  - **The Tasks tab** reads the same run rows, then the task rows of the runs on its page only (`pipeline-execution-index`), and pages on the start of its last run. With a status, it reads no run whose summary has no row of it (a running task may still show as `deps_ready`), and a page ends at a run once it has read about 20,000 task rows, with its cursor (`test_a_status_no_run_has_reads_no_task_row`, `test_a_run_whose_tasks_were_stamped_after_a_newer_runs_is_not_skipped`, `test_an_hourly_pipelines_runs_page_through_every_run`).
  - **A date filter** still reads the task rows of its one logical date (§4), with no window. In the Tasks tab a day finds the runs of every granularity whose partition holds it: the day, its hours, its ISO week and its month (`feed.day_keys`).
  - **The pipelines list** (`/api/pipelines?stats=true`, polled every 30 seconds) reads the run rows of 14 start days. A pipeline's `status` and `waiting_on` come from its latest run's summary; `recent_runs` is the last 10 runs whose logical date is within the 14 days, newest first by date, then `started_at`. Its API stays as ADR #136 defines it, and `stats_incomplete` means a start day that could not be read.
  - **The pipeline page's runs** (`/api/pipeline-executions`) read the same run rows with a filter on `pipeline_name`. The history walks the start days newest first; a range walks every start day of the 90-day window with a filter on `run_date` too. Only an opened run reads its task rows.
  - **A run can start before its logical date** (the Run dialog fills in the browser's local date), and a run for a later date started today is valid. So a list reads start days alone only where it orders runs by their start (the Runs tab, the pipeline page's history); a list keyed by logical dates walks its whole window. A range misses a run that started more than 90 days ago; the pipelines list misses a run that started before its 14 days for a date within them.
  - **No route asks Step Functions about a run** (§4). The console's remaining calls concern pipelines and tasks: `StartExecution` of a run started from the console, `ListStateMachines` for the health check and for a pipeline the registry has no ARN for, and `StopExecution` of a task's `run_task` after an action.
  - The costs: a run stopped in the AWS console is stopped within seconds (§7), or, if that event is lost, shows `running` until the run row's next check, up to about 35 minutes. After the upgrade the pipelines list shows no 1.2 run: a pipeline's status appears with its first 1.3 run.
  - The UI takes each window from its own constant, and a parity test pins each to the console's (Principle #28).
  - The index is a DynamoDB schema change the maintainer approved (Principle #6), and the only index 1.3 adds (*Migration and upgrade*). While DynamoDB builds it on an upgraded table, its reads answer "backfilling"; the Runs tab and the pipelines list treat that as transient and say so. CloudFormation reports the table updated while the index still builds (about 8 minutes on 100,000 rows), so `polyris-up` waits for the index to become active and shows that it waits.
- **Pause.** A pause means "start nothing": the run's ready tasks stay `waiting_paused`, and a pass over a paused run starts no row, not even a `deps_ready` one whose start failed. Tasks that already run go on. A pause lasts until it is lifted.
  - **The run row holds the pause.** Pause opens an interval and Resume closes it, each a conditional update of the run row, which keeps at most ten intervals (§3). The 1.2 pause row goes.
  - **No start after a Pause.** A Pause raises `run_version`, which every `deps_ready` transaction checks (§1), so a Pause after a pass's read holds every row the pass has not yet written `deps_ready`, as a Stop does (§4). A row written `deps_ready` before the Pause still starts.
  - **One owner per question.** A pause's time counts toward no waiting limit, for dependencies or for a decision: the deadline function moves each deadline by the paused time inside its wait. `trigger_rules.enabled_at`, from which the deadlines and the countdown count, reads no pause. Only the sweeper's lost-hint check reads the resume, through an enabling time never before it (ADR #130 §9), so no pause is counted twice: the clamp to `resumed_at` in `sweep.lost_hint` serves that check only.
  - **Due times in a pause.** While the run is paused, a `waiting_paused` row, a `deps_ready` row whose start the pause holds and a row's limit on its wait have no due time (invariant 9). A decision deadline keeps its entry, which the bell reads whatever its time, and falls due far in the future; the bell shows no deadline for it. A pass removes or postpones these due times with the `ConditionCheck` on `run_version` of §1, so a Resume after its read keeps them.
  - A pause does not stop a countdown: a task whose `wait_before` ends inside a pause starts when the pause is lifted.
  - `/api/execution-extend` and the console's "+12h" button go.
  - On resume, every ready task starts at once. Resume closes the interval, and the run row's change reaches the dispatcher through the stream (§7): the pass decides the `waiting_paused` rows, starts the `deps_ready` rows the pause held, and sets each limit's and decision deadline's due time again, moved by the paused time. Rows it does not reach within its budget are left to the next pass, which `left_at` wakes at once; they are no lost hints (§7, Rule 52). A Resume whose stream record is lost is found at the run row's next check, up to 30 minutes later.
- **The run's safety limit.** `Start_Run` waits for its token for one year, the longest a Standard execution runs, whatever the DAG: no derivation, no margin, no heartbeat. The task limits and the sweeper do the work, and a broken engine shows in the System status (§6). A run whose execution reaches the year is stopped like any run whose execution ended before its answer (§4).
- **`bulk_backfill`** waits for each run as long as the run lives.

### 6. Failure visibility

The three levels of ADR #130 §9 stay; what fills them changes.

1. **Heals itself.** A start is repeated under the same name when its next try comes. The sweeper checks every due row, and a run row's check judges every row of its run and puts back a lost due time (invariant 9). Both streams retry a failed batch, and `run_task` retries its success transaction after a conflict. Every pass has a time budget: one that runs out wakes the next through `left_at` and leaves its run row due, instead of failing its batch (§7).
2. **Fails loudly.** A non-transient error of the dispatcher writes `failed`, with the cause, into the row itself.
   - A start refused for good, and a `run_task` execution that ended without an outcome, make the row `failed` with the error and the cause. A success that cannot be recorded makes the row wait for a decision, with the cause (§1).
   - A `deps_ready` row whose start keeps failing writes one `coordination` warning after 15 minutes and fails after 6 hours (§5).
   - A missing row fails its waiting dependants, with a warning (invariant 11).
   - A `Start_Run` that fails for good writes a `coordination` warning with the run and the cause, and the execution fails after the `Parallel`; the rows of a run that never became active are stopped with the execution's error (§1, §4).
   - A failed direct step writes a `step` warning and marks the run row, and the run's execution fails once every branch has ended (§1).
   - The rows of a run whose execution ended before its answer are stopped with the cause (§4).
3. **Shows engine health in the console.** The sweeper's self-check and the System pill cover the tasks table's stream and its event source mapping as they cover AssetFanout's: the mapping's state and its `LastProcessingResult`. An `AccessDeniedException` in the dispatcher shows there too (§7). No custom metric, alarm or topic (Principle #45).
   - The oldest overdue row, which may be a run row, shows a sweeper that cannot keep up. It does not show a stopped stream consumer: the sweeper's passes run in its own process.
   - A stopped consumer, or a shard held by a record that keeps raising a transient error, turns the System status red through the mapping's state or `LastProcessingResult`; but one held shard among healthy ones may show only now and then (`LastProcessingResult` reads OK again as soon as a healthy shard processes a batch). So the sweeper's report also counts the runs whose check found lost hints, `engine_findings` shows a count above zero, and each run held back gets a lost-hint warning at its run row's checks (§7). Those runs go on at their run rows' checks, up to 30 minutes apart, and a held record leaves the stream after 24 hours.
   - An engine whose every pass fails (a parse error after a format change, for example) ages no entry, since each failed pass moves its run row by the backoff; it shows through the sweeper's count of failed passes instead (§7).

**The bell finds failures by when they happened.** A failure of a run of an older date must show (a `wait_for` task fails at its 7-day limit), so the bell reads `attention-index` only, with no new index and no new kind of row:

| Kind | Rows | `attention_at` | Read by |
|---|---|---|---|
| `waiting` | a task row with a time of its own (invariant 9): `waiting` with a limit or a countdown, `deps_ready` or `running`; the run row while it is due (§3) | its next check | the sweeper, once due |
| `decision` | a task row `waiting_decision` | its decision deadline; far in the future while its run is paused (§5) | the sweeper, once due; the bell, every entry |
| `failed` | a task row `failed` | when it failed | the bell, within its window |
| `retry` | a push start to retry | its next try | the sweeper |
| `warn` | a warning row | when it was written | the bell, within its window |

- A row's entry follows its status and times (§3), so the write that changes them replaces or removes it. A Restart removes a `failed` or `decision` entry, and writes a `waiting` one only for a row with a limit outside a pause. There is no `paused` kind.
- The run row reuses the `waiting` kind: its only reader is the sweeper, which groups due entries by run, and the `_run_` key tells them apart (a kind of its own would add 16 shard queries to each sweep and to its self-check).
- The index keeps its projection (a change would replace it): the status, task, pipeline, run, error and `task_date` (§3).
- The bell reads every `decision` entry, and the `failed` and `warn` entries of its window, from the 16 shards of each kind. It keeps one notification per run, a decision request over a failure, and adds the warnings and the backfills. A notification's id names its event (the task row and when its entry falls due), not its run, since the console keeps "read" by id and a run goes on after a failure.
- A failure outside `run_task` (a wait limit, a decision timeout, a Fail, a `run_task` that died) shows there like any other.

### 7. Wake-ups

A hint only says "check again". The dispatcher's writes, its starts and the run's answer are decisions, which a lost hint never undoes (Rule 41).

| Source | Wakes the dispatcher for |
|---|---|
| A DynamoDB stream on the tasks table, through an event source mapping | the run of a row whose transition the *Wakes* column of §3 marks: a task row that became final or `waiting_decision`, moved from a final failure to `success` or `skipped`, or was restarted; a run row that became active, was paused or resumed, received a request, or whose `left_at` a pass set |
| The stream on `asset-events`, through AssetFanout | a narrow pass over each run with a task that waits for the asset (below) |
| The sweeper, every 5 minutes | the run of every row that is due |
| An EventBridge rule on the default bus (`ExecutionEndRule`) | the run whose execution, or one of whose rows' `run_task`, ended `ABORTED`, `TIMED_OUT` or `FAILED`, unless the engine stopped it itself (below) |

- **The end of an execution** is a hint like the others: the pass decides from the rows and `DescribeExecution`, as the sweeper's check does. Without it, an execution that ended without a write was seen only at that check, up to 35 minutes later (`attention.BACKOFF` and the sweep's 5 minutes).
  - The rule matches Step Functions' *Execution Status Change* events of `ABORTED`, `TIMED_OUT` and `FAILED` executions of this platform's `run_task` and of every polyris state machine (`*-polyris-*`, since a pipeline takes the namespace and stage of its own `config.py`), whose `error` is `null` or anything but `Polyris.Stopped`: the engine's own stops (`dispatcher.STOPPED_ERROR`) make no event, so a Stop of a large run makes no invocation per row. The pattern names `"error": null` because EventBridge leaves `anything-but` on `null` unstated (`events:TestEventPattern` confirmed the pattern). No queue, DLQ or failure destination (Principle #45).
  - The dispatcher reads an event (`source` `aws.states`) apart from a stream batch; a dispatcher older than the rule reads it as a batch without records, so the order of a stack update does not matter. A cheap read comes first, the run row `_run_{name}`: no run row (`bulk_backfill`, the test state machines, another platform) or another execution than the one the run row records ends there. Otherwise one full pass makes the engine's check of the run's execution now (`engine_check_due` keeps its conditions), never the sweeper's whole check, which also judges lost hints.
  - The end of a `run_task` names its row through the execution's input (the row's key, generation and run, `run_task_input.Key`). An event leaves out an input over 248 KiB: that end is a lost hint the row's check covers. An input that names no 1.3 row wakes nothing. One read of the run row and the row comes first: the event wakes a pass only for the `run_task` of the row's current generation, under its derived name (invariant 4), and that pass's check of the row comes now (`judge_now`, `dispatch.liveness_due(at_once=True)`); a failed start's next try and a pause keep holding it (§5). An event that cannot be read is logged and dropped; a transient failure is raised, and Lambda retries an asynchronous invocation twice.
  - A lost event costs the row's or the run row's next check; a duplicate finds the run stopped or the row final; an end of an older generation names another execution than the row's.
- The tasks table's stream replaces `notify_dependents` and `query_subscriptions`. It carries every writer's change, so no writer has to remember to notify (ADR #130 chose the fact table's stream for the same reason).
- **The filter comes from the transition table.** The stream carries both images (`NEW_AND_OLD_IMAGES`), so each pattern names an old and a new value. The patterns are generated from the *Wakes* column of §3 or pinned to it by a parity test, and the harness's stream adapter uses the same predicate (Principle #42): a hand-kept list would lose the wake-up of a transition added later, found only at the run row's check with a misleading lost-hint warning.
  - Each task-row pattern requires `generation`, a field only task rows carry (`output#` and warning rows have a `status` too, §9).
  - The patterns take four of the five filters Lambda allows per mapping by default: three for task rows (became final or `waiting_decision`; restarted; a final failure that became `success` or `skipped`) and one that lets every insert and change of a run row through, since a filter cannot compare a field's old and new values. A task-row filter says "became" through the old image: a final or `waiting_decision` status in the new image and an `anything-but` of the final statuses in the old.
  - A filter may let through more records than the predicate wakes for, and the dispatcher drops the rest with the same predicate (a `waiting_decision` row rewritten in a pause; a run row write the *Wakes* column does not mark, unless it changes `left_at`). On task rows, due-time and TTL writes match no pattern, nor does a TTL deletion.
  - A test runs every transition of the table through the template's `FilterCriteria` and the predicate, with fixture records for an insert without an `OldImage`, an `output#` row, a warning row, a TTL write and a run row's summary write.
- **Batches.** The mapping takes the batch and retry settings of the asset-events mapping (ADR #130 §6.1), with no on-failure destination, and a batching window (`MaximumBatchingWindowInSeconds`) of 1–2 seconds. It starts at `TRIM_HORIZON`: a new mapping that started at `LATEST` missed the records of its first two minutes. The dispatcher groups a batch's records by run and makes one pass per run. Its `ParallelizationFactor` is above 1 but small (a new account may run only 10 Lambda invocations at a time, shared with the platform's other functions). Two passes over one run at once are safe: every write is conditional and every start has a derived name.
- **A pass over a `creating` run returns at once.** The run row's insert passes its filter and the predicate drops it; `Start_Run`'s task-row inserts match no filter (an insert has no `OldImage`).
- **Time budgets.** Every pass has a time budget below its function's timeout, whoever calls it (Rule 52). A pass that does not reach every row of its set makes its run row due at once (§3) and sets the run row's `left_at` to its own time, when it wrote something or when `left_at` is absent.
  - A change of `left_at` wakes the dispatcher through the stream, so the next pass goes on at once (or the sweeper within 5 minutes if the record is lost): the start of 2,000 root tasks, or the Resume of a large run, goes on in passes back to back.
  - A run where no write gets through wakes at most one more pass this way, so passes never loop without progress. The sweeper's check clears `left_at`, and rows it finds while `left_at` is set are no lost hints.
  - The mapping retries a failed batch forever (`MaximumRetryAttempts: -1`, `MaximumRecordAgeInSeconds: -1`), so a pass that kept timing out would hold its shard for 24 hours; the budgets prevent that.
- **Conflicts.** Every decision's transaction checks the run row, so a pass sends a run's transactions one at a time. Two passes over one run, or a pass and an action, can still cancel each other's writes (`TransactionConflict`, which the SDK does not retry): a pass retries such a write after a short random backoff within its budget, and the console does the same for an action. A row a pass leaves for a conflict is left through `left_at` and is no lost hint.
- **Errors.** A record raises only on a transient error. Anything else ends in the row or in a warning, so one bad record never holds up its shard (Rules 51 and 52). An `AccessDeniedException` is not transient and fails no row, a denied start included (§5): it writes a `coordination` warning, shows in the System status and leaves the row to its next check, so the run goes on once the permission is fixed. Root `CLAUDE.md` makes this the stream consumers' exception to raising `AccessDeniedException`.
- Adding a stream changes the table in place (CloudFormation does not replace it); it is a schema change the maintainer approved (Principle #6).
- **Reads.** A full pass reads the run row, then the run's task rows by key, from the task names of its spec version (§3), with consistent reads and no index on the decision path. `attention-index` keeps its keys and projection (§6). `date-pipeline-index` keeps `wrapper_execution_arn` in its projection, though nothing writes or reads it: a change of projection replaces the index.
- **Logs.** A pass writes one log line, with its run and counts, and one per row it changed; none for a row left as it was (a line per row per pass would grow as N², like the reads). A harness test counts the lines of a pass over a run where nothing changed.
- The `asset:{name}` pointers stay in `dep-subscriptions` for AssetFanout; the task-dependency pointers go. The dispatcher deletes a row's pointers once it has left the dependency wait (`waiting` and `waiting_paused`), and a restart writes them again (Rule 40).
- **An asset wake is a narrow pass.** AssetFanout passes over each run with a task that waits for the asset: it reads the run row, the rows the asset's pointers name in that run and their direct upstreams, by key, and decides them with the same `decide`. The full pass is the same code over every row (one entry point takes a set of rows, so the logic cannot fork). A narrow pass leaves the run's end and summary to the next full pass, which the stream starts once a status changes. (A full pass per wake would read about 16 million rows for 90 facts on a 2,000-task pipeline waiting for 90 dates.)
- **The sweeper** keeps its lease, budget, backoff and schedule. It reads the due entries of the `waiting` and `decision` kinds (§6), run rows included, groups them by run and makes one full pass over each, which decides every waiting row and judges every row from the row itself (§1):
  - a `waiting` row at the end of its countdown is decided again, and starts if still ready and the run is not paused; one past its limit fails, unless the run is paused (§5);
  - a `deps_ready` row whose next try has come is started again unless its run is paused or being stopped, and a failed attempt counts toward its deadlines (§5);
  - a `deps_ready` or `running` row whose liveness check has come has the execution of its current generation judged, and fails when that execution ended without an outcome (§3);
  - a `waiting_decision` row is checked against its deadline, which a pause moves (§5);
  - a run row still `creating` after `Start_Run`'s retry window is stopped (§4); an active one has its execution checked, its requests carried out and its end decided (§4).

  The pass writes only what changed; the sweeper then moves the run row's due time on and clears its `left_at`, one small write per run (§3).
  - **A pass that fails** leaves its run to the backoff too: the sweeper moves the run row's due time and writes a `coordination` warning with the cause. A pass that failed for good marks the run row (`check_failed`), and until its due time the sweeper leaves a marked run, whatever rows of it are due, so one broken run (one whose spec item was deleted by hand) does not take the budget first at every sweep. Its rows stay due, so after 40 minutes the System status says waiting tasks are behind their checks.
  - The warning's key is its kind and the run (`records.warning_item`), so each failed check replaces the same row.
  - The sweeper's report counts its passes and the failed ones. A sweep in which more than half the passes failed, and at least two, adds a failed step with the count and the first cause, which `engine_findings` shows; with few active runs the runs' warnings in the bell are the sign.
  - **Lost hints.** A row whose wait the pass ends is a lost hint only when its enabling time is older than the check's time minus `LOST_HINT_GRACE` (5 minutes, longer than the stream's batching window and its retries). Neither a row whose countdown ended nor a row found while the run row carries `left_at` counts. The check writes one `sweeper` warning per run, with the number of lost hints and a few task names.

  Push retries, the push catch-up and the self-check stay; the pause-release step and the adoption scans go.

### 8. Task specs and pipeline limits

A task's spec is everything needed to run and draw the task: type, resource, configuration (`task_config`, ADR #108, TaskConfigKey), dependencies, trigger rule, limits and retries, `wait_before`, outlets, inlets, `wait_for` and `skip_on_backfill`. The specs live in a table of their own, so a pipeline's size has a limit of ours, not those of a Step Functions state or definition.

- **What a task row carries.** Only what the dispatcher decides on: the dependencies, the trigger rule, the limits, `wait_before`, `wait_for` and `skip_origin`, with the `spec_id` and the hash of the task's spec text, about 1 KB besides the status fields and those the console reads (§3). The dispatcher reads the full spec once per start (§1), so the cost of a pass, which reads every row and is billed by item size, does not depend on the size of a spec (a daily 2,000-task pipeline costs an estimated $17 a month in DynamoDB with 1 KB rows, $95 with 20 KB rows).
- **The table, `pipeline-specs`**, on demand, with the billing tags (Principle #54), string partition and sort keys, holds two kinds of item:
  - **Texts:** partition `{pipeline}#text`, sort key the sha256 of the text, the task's spec as one string attribute; a text is stored once, however many versions use it.
  - **Versions:** partition `spec_id` (`{pipeline}#{fingerprint}`), sort key `task_id`, with the hash of that task's text. A version's fingerprint is the sha256 over its `(task_id, text hash)` pairs in key order.
  - A text is canonical JSON (`sort_keys`, compact, `ensure_ascii=False`, `allow_nan=False`): DynamoDB stores `1.0` as `1` and keeps no map order, so a hash of attributes read back would not match the deploy's (moto keeps both; only a live table shows it). Every reader checks the sha256 of each text it reads.
  - No TTL (a template test pins it), and no deletion protection, which would make `polyris-down` and the rollback of a failed first install fail. The table goes with the platform stack.
  - Versions and texts never change and are never deleted: a redrive runs the original definition for up to 14 days after its execution ended, and identical DAGs share version items. A destroyed pipeline's specs stay until the platform is removed. No point-in-time recovery: the specs are derived, and a redeploy writes them again.
- **`polyris-deploy` writes the specs before the stack.** (1) It writes each text the table lacks, with a conditional put that counts a text already there as written, then every version item, retrying `UnprocessedItems`; an access-denied error stops the deploy. (2) It reads the version back with a consistent query and its texts with `BatchGetItem`, and checks the count, each text's hash and the fingerprint. (3) Only then does it create the change set. The definition carries `Start_Run`'s arguments: the format, the full `spec_id` and `task_count`. No state's input carries a spec.
- **`Start_Run` checks what it reads.** The format first; then the version with a strongly consistent, paginated `Query` and the texts with `BatchGetItem`, retrying `UnprocessedKeys`; each text's hash and the fingerprint; each spec parsed, and one with a key it does not know rejected (§9). A fingerprint or hash that does not match, a missing item or a `task_count` of 0 fails `Start_Run` before it writes a row, and its `Catch` writes the warning (§1). Throttling is transient and never counts as a missing spec. A pipeline without tasks has no `Start_Run` and no run row: its direct steps run alone (§1).
- **Registration and the graph.** A state input that carried every task's metadata passed 256 KB at about 245–460 tasks, and the registry item reached DynamoDB's 400 KB at about 420–800 tasks.
  - `Register_Pipeline` writes the `spec_id` and `task_count` into the registry instead of the tasks' metadata. The pipeline's own state machine writes them, so the registry follows a CloudFormation rollback. Its `Catch` names `States.DataLimitExceeded`, as AWS documents it outside `States.ALL` (B2).
  - The per-run DAG snapshot becomes the run row's `spec_id`: a spec version never changes, so it names the graph the run ran with. `Save_DAG_Snapshot` goes, with its rows; since 1.4 the console reads no snapshot of a 1.2 run (*Migration and upgrade*).
  - The console draws a run's graph from the specs of its run row's `spec_id`, and a pipeline's from the registry's. Direct steps are not graph nodes (`generators.py` excludes them); a failed one shows through the run's status and its warning.
  - **Every other reader of the registry's `tasks` and `dag` moves to the specs,** through one accessor of the console's DAL (`upstream_integration.py`, `routes/pipelines_info.py`, `routes/tasks.py`). A reader left behind would read a missing field as empty and fail silently (a backfill would run the tasks its user excluded with `skip_on_backfill`), so a census test (`test_registry_readers.py`) fails for any code that reads the registry's `tasks` or `dag`.
- **The limits are ours.** `polyris-deploy` and `polyris-validate` refuse a pipeline beyond any of them, with the limit and the measured size.
  - **Tasks per pipeline:** a declared maximum of about 2,000, an estimate from the harness and AWS's published prices and quotas, not a live run of that size (*Tests*); it holds given four limits: `run_task`'s history (below), the Tasks tab's read of a pipeline (§5), the dispatcher's cache of spec texts, and the sweeper's `DescribeExecution` calls (§1). `Start_Run`'s timeout and the sweeper's window for a run row still `creating` derive from it (§1).
  - **Outlets per task:** 97. A transaction holds at most 100 items; `run_task`'s success writes the status, the output and a fact per outlet (§1), and Mark Successful also raises the run row (§3).
  - **Bytes:** each task's spec, outlets included, against `run_task`'s 256 KB input; the spec with the statuses of all its upstreams at their longest (any status, since `one_success` and `one_failed` start beside running upstreams) against the same 256 KB, less the date variables a Lambda's or state machine's payload adds; an ECS task's container overrides with the environment `run_task` adds (the upstreams' statuses included) against ECS's 8,192 characters, and a Batch SubmitJob request with that environment against 30 KiB; the specs together against 16 MB, which `Start_Run` reads at once; and the definition against Step Functions' 1 MB as `polyris-deploy` sends it (`indent=2`).
  - **History:** `run_task`'s events with every upstream and retry, `52 + 46R + 7K(R + 1)` for K upstreams and R retries, against 22,500, a tenth below Step Functions' 25,000 per execution.
  - **Duplicate outlets:** the decorator rejects the same asset twice in a task's `outlets`: two puts on one key would cancel the success transaction for good.
- **IAM and tests.** The role that runs `polyris-deploy` needs `dynamodb:PutItem`, `BatchWriteItem`, `BatchGetItem` and `Query` on `pipeline-specs` (*Migration and upgrade*), and for `polyris-destroy` `states:ListExecutions`, `states:StopExecution` and `dynamodb:DeleteItem` on `pipeline-registry` and `asset-subscriptions` (§4). A test ties the deploy policy in `IAM_PERMISSIONS.md` to the calls in `deploy.py`. A fault-injection test drops or alters a version item or a text, and the deploy must stop before `create_change_set`. Golden spec files show what a generator change does to the specs and expose a shape change made without a format bump.

### 9. Contracts and pure functions

A value two pieces of code must read alike gets one named constant, and a parity test where it crosses a file or a language (Principles #13, #27 and #28).

## Migration and upgrade

**Path:** 1.1.4 → 1.2 → 1.3 → 1.4. Since 1.4 the platform upgrades from 1.3 only: `polyris-up` refuses a platform below 1.3 before it changes anything, and the move from 1.2 is made with the `polyris-up` of 1.3 (its checks, the drain, the stop of what 1.2 left running and `--accept-stopped-runs`: `v1.3.2:docs/decisions/adr-137-tasks-as-rows.md`, this section). 1.4 removes the code that served 1.2 runs (D6):

- **A row a 1.2 run left in flight** has no readiness fields and no run row. No pass starts or stops it: the sweeper's pass skips it with a log line, never a warning, and it expires with 1.2's TTL. The fence of every task-row write has no branch for a row without a generation, and the transition table knows no status that only 1.2 wrote (`test_a_1_2_row_left_in_flight_is_skipped_and_warns_at_no_sweep`).
- **A 1.2 run in the console** has no run row. One with a row left unfinished shows `running` until its rows expire, and its graph is the pipeline's current one: the console reads no 1.2 DAG snapshot. The skip of `dag_snapshot::` rows in `should_skip_token_row` and `task_row` stays while such rows can exist.

**Every pipeline is redeployed.** 1.3 deletes `dependency_wrapper` and the other old helpers with no adapter and no stub, so a pipeline not redeployed fails at once (its start of the wrapper is refused with `StateMachineDoesNotExist`); nothing hangs. Three things make a forgotten or mismatched pipeline visible:
- At the end of the upgrade, `polyris-up` lists the pipelines that still need a redeploy, with the command for each, found in the registry as `polyris-down` finds them (ADR #131).
- `polyris-deploy` records a pipeline format version in the registry, one integer, a deploy-owned field written with `registered_at`. The console marks a pipeline whose version is missing or older than the platform's "redeploy needed". The value is one SDK constant both sides read (Principle #28).
- The same version travels in `Start_Run`'s arguments, and `Start_Run` refuses a format it does not support (§1). A deploy across this change stops earlier: `polyris-deploy` reads the platform stack's outputs, and the wrapper's output goes while `Start_Run`'s comes.

**The deploy role first.** Before the upgrade, add `dynamodb:PutItem`, `BatchWriteItem`, `BatchGetItem` and `Query` on `pipeline-specs` to the role that runs `polyris-deploy` (§8), and `states:ListExecutions`, `states:StopExecution` and `dynamodb:DeleteItem` on `pipeline-registry` and `asset-subscriptions` for `polyris-destroy` (§4). Without them every redeploy stops at the write of its specs, with the cause.

**Runs from 1.2 in the console.** They have no run row and no `spec_id`. The Runs tab, the pipelines list and the pipeline page's history and ranges show only runs started on 1.3 (§5); the pipeline page for a chosen date and a date filter still find the older ones until their rows expire, 31 days after their last write. The bell shows no failure of a 1.2 run, and no action applies to it (above).
- **Their backfill records** carry no `date`, so the search of backfill records no longer finds them; they drop out of the bell and the runs feed, and expire 30 days after their creation.

**The template change** is one change set; the CHANGELOG's "Upgrading to 1.3.0" gives the steps.
- **Added:** `Start_Run`'s function, with its role and log group; the tasks table's stream and its event source mapping; `run-start-index`; the `pipeline-specs` table; the stack outputs `polyris-deploy` reads (`Start_Run`'s ARN, the name of `pipeline-specs`).
- **Removed:** eight state machines and their seven log groups; the `query-subscriptions` function with `QuerySubscriptionsRole`, `QuerySubscriptionsLogGroup` and `QuerySubscriptionsPermissionFromSfn`; the `DependencyWrapperArn` output with its export (a stack that imports it stops the update). The 1.2 wrappers' logs go with their log groups.
- **IAM:** the dispatcher's role reads the tasks table's stream (`dynamodb:DescribeStream`, `GetRecords`, `GetShardIterator`, `ListStreams`) and `pipeline-specs`, and may start, describe and stop `run_task` and pipeline executions and answer a run's token. A pipeline takes the namespace and stage of its own `config.py`, so the grants on executions cover every polyris state machine (`*-polyris-*`; a pipeline is named `{namespace}-{stage}-polyris-{dag_id}`), not the platform's prefix alone (`test_the_engines_grants_on_executions_cover_a_pipeline_of_any_namespace`); the code acts only on the executions its own rows record.
  - The sweeper's role gains `dynamodb:DescribeTable` on the tasks table and reads `pipeline-specs` through the dispatcher's managed policy. `Start_Run`'s own role writes the run's rows and pointers and reads `pipeline-specs`. `ConsoleApiRole` may read `pipeline-specs`; its grant on `pipeline-tokens/index/*` covers the new index. The console's routes call no `DescribeExecution`, and the role loses the calls that answered or kept alive a token and `ListExecutions` (a test holds the role to the calls made under it).
- **Names kept:** the dispatcher keeps every logical ID and physical name of `reconcile` (function, role, managed policy, log group): a rename would replace them, and the managed policy's fixed name would collide (`EntityAlreadyExists`, Principle #33).
- **Tables:** the change replaces or removes no table. DynamoDB creates at most one global secondary index per table update, so `run-start-index` is the only index 1.3 adds; CloudFormation takes the index and the stream on one table in one update, with the new table and the deletions, and a rollback of that update restores the table.
- **Template tests:** `pipeline-specs` has no TTL, no `DeletionProtectionEnabled` and no `Retain` policy (a table a rollback left behind would block the next `polyris-up`). The mapping's `FilterCriteria` is checked against fixture records (§7).

**A failed update rolls back.** `polyris-up` rolls back a failed update by default; CloudFormation deletes removed resources only in the cleanup after a successful update, so a rollback restores all of 1.2. With `--disable-rollback`, the update keeps what it changed and is fixed forward.

## Consequences

**Version.** The release is 1.3.0, though by the letter of SemVer it is a major one: a 2.0 before there are users would spend the major version on an internal rewrite. The CHANGELOG opens with a "Breaking" block and states the policy:

> Until 2.0, a minor release may change how runs behave, remove console routes, stack outputs and DSL parameters that had no effect, add deploy-time limits, and require upgrade steps. Each such change is listed under "Breaking", and `polyris-up` checks the upgrade's preconditions itself.

**For the user** (the 1.3.0 CHANGELOG lists each): every pipeline needs a redeploy after the upgrade; a failed task no longer ends its run at once (§4); a Stop is final for its run; the work of a task has no time limit by default and `execution_timeout` limits each attempt (§5); a pause lasts until it is lifted; limits fire up to 5 minutes late; outputs and statuses reach a task from its own run (§1); a run whose only failure is a direct step shows `failed`; the bell shows every failure of its window whatever the run's date; histories are kept longer (§5); a pipeline may hold about 2,000 tasks (§8).

`DAG` loses thirteen fields that nothing read (`timetable`, `catchup`, `default_timeout`, `params`, `template_searchpath`, `template_undefined`, `render_template_as_native_obj`, `max_active_tasks`, `max_active_runs`, `dagrun_timeout`, `sla_miss_callback`, `access_control`, `doc_md`): a `dag.py` that sets one fails with an error that names it. `polyris.TERMINAL_STATUSES` and `FAILURE_STATUSES` keep their members and the engine reads neither: a row is final by `SETTLED_STATUSES`, which holds `stopped`, and a trigger rule counts `stopped` as a failure through `transitions.FINAL_FAILURES` (ADR #138); merging the public sets would move the console's counters.

**Operations.** 13 state machines become 5, and the `query-subscriptions` function goes. `Start_Run`'s function lives in the coordination package (`sam/lambdas/coordination/`), with its own role and log group. The tasks table gets a stream, an event source mapping to the dispatcher, and `run-start-index`. A new table, `pipeline-specs`, holds the specs (§8). The docs that count resources change with the template (`make test-docs`).

**Cost** (estimates at on-demand prices in us-east-1 as of 2026-11-24, counted on the coordination harness):
- **Step Functions.** A task takes about 15 Standard transitions (13 in `run_task` and one per upstream whose output it reads, plus 6 per run in the pipeline's state machine), where 1.2 took about 47; a retry adds 14 and one per upstream. A waiting task costs nothing (ADR #19).
- **The total.** At 1,000 tasks a day in daily pipelines of 10–50 tasks, about $13 a month without the console ($0.40–0.43 per 1,000 tasks, 87% Step Functions), plus $0.35–0.7 of storage and $0.10 for the idle sweeper. A daily 2,000-task pipeline costs about $26–40 a month.
- **The full passes grow as N².** A run of N tasks makes up to about N full passes, each reading every row with a consistent read: a 2,000-task run reads about 4 million rows, about $0.5 per run (from N/10 to N reads a task, as its tasks finish in bursts or one at a time). It stays below 1.2's Step Functions cost for as many tasks.
- **What multiplies it:** the size of a task row (about 1 KB, since the spec stays off it, §8); the run row's checks of a waiting run, a full pass each at most 30 minutes apart, which write only changed due times; `wait` reasons that change at every pass (they hold no time, and a test pins that they are written only when they differ, §1); the five index writes of a task row's status write; transactions, which bill both items at twice the units; the logs, which is why a pass logs one line plus one per changed row (§7); point-in-time recovery; and the size of `output#` (up to 350 KB, a year) and `input#` (up to 380 KB, 90 days).
- A narrow pass makes an asset wake cost a cent where a full pass would cost about $2 (§7); storing each spec text once keeps spec storage near $0.2 a month (§8); keeping the run row under 5 KB keeps its checks under a cent a run (§3).

## Alternatives considered

- **A thin wrapper** (`dependency_wrapper` keeps its ARN and becomes "write the row and end"): it existed only to spare a redeploy, which is mandatory, and it would keep both a token per task and the run's end at the first final failure.
- **A run as a row too, with no state machine per pipeline:** nobody has asked for it (Principle #18); `bulk_backfill` waits for each run through `startExecution.sync:2`, the direct steps would need a new home, and it would be a 2.0.
- **Polling in the wrapper:** its cost, and the 25,000-event history limit of an execution.
- **Compiling the DAG into ASL:** it cannot skip a task, mark one successful or pause a live run.
- **Lambda durable functions:** the same model of a process waiting on a token.
- **An explicit call to the dispatcher from `run_task` and the console instead of a stream:** every present and future writer would have to remember it.
- **Only the sweeper to find an execution that ended without a write:** a run stopped in the AWS console showed `running` for up to 35 minutes, so the EventBridge rule of §7 wakes the run; the event stays a hint, and the generation is checked against the row. Rejected beside it: a sweeper every minute or a shorter backoff (still minutes, and more calls on a rate-limited API); a `Catch` in the state machines (it does not run on a stop from outside or the execution's own timeout); a function of its own with reserved concurrency (an account at the default limit of 10 cannot deploy it; the rule's filter removes the burst instead); polling `ListExecutions`.
- **The task specs from the registry or from the run's DAG snapshot:** the registry lacks the specs, both are written best effort by a state with the same 256 KB limit, and a redeploy changes the registry under a waiting run.
- **Every spec in `Start_Run`'s arguments:** a state's input holds 256 KB, about 250–600 tasks.
- **`Start_Run` reads its own definition** (`DescribeStateMachineForExecution`): the 1 MB cap stays, the call refills at 1 per second per account and Region, and AWS documents it as eventually consistent and best effort.
- **The specs in chunks across several `Start_Run` states:** they stay under the 1 MB cap of a definition.
- **The specs as one object in S3:** a second service on the path that starts a run, with a bucket and a cleanup of its own.
- **The full spec on every task row, or every spec copied into each spec version:** every full pass reads every row and is billed by item size, and storage would grow with each deploy (§8).
- **The run's input on the run row:** the run row is checked by every decision's transaction, so its size is paid at every decision (§3).
- **Checking each direct upstream's generation in a decision's transaction:** a task with more than 99 upstreams cannot fit; one `ConditionCheck` on `run_version` does the job (§1).
- **A full pass for every asset wake:** about 16 million row reads for 90 facts on a 2,000-task pipeline (§7).
- **The run lists deriving each run's status from its task rows:** a page of 25 runs of 2,000 tasks would read about 50,000 rows.
- **The pipelines list checking each `running` latest run with `DescribeExecution`:** runs wait for days, so 60 waiting pipelines in 5 open consoles would make about 10 calls a second, the smallest refill rate AWS documents, shared with the dispatcher.
- **A new index or kind of row for the bell:** `attention-index` already orders rows by when they need attention (§6).
- **A due time for every unfinished row** (ADR #130 invariant 5): each check rewrote every due row, so a large pipeline waiting for data paid for its size at every check (about $840 a month for 90 waiting runs of 2,000 tasks, against about $33).
- **A restart counter on the run row raised only by Restart and its resets:** a Skip or Mark Successful of a final failure, a new token and the answered mark left it unchanged, so a decision or the removal of the due time could stand on a stale read (a `one_failed` cleanup could run after an operator declared its upstream good). `run_version` is that counter, raised by every such write (§3).
- **No due time of its own for a `running` row:** one full pass would then call `DescribeExecution` for every running row at once, where the rows' own due times spread the calls.
- **Bookkeeping on each row a pass left,** to tell it from a lost hint: the grace and `left_at` do the same with no write per row (§7).
- **Refusing a run whose logical date is after its start day:** the Run dialog fills in the browser's local date, and a run for a later date is a valid request; a range walks the 90 start days instead (§5).
- **The pause flag as a row of its own:** one more kind of row, with its own stream pattern, TTL and read per pass.
- **Facts written in batches before the status,** to lift the cap of 97 outlets: a batch put takes no condition (it overwrites another producer's fact of the same millisecond, and Step Functions counts `UnprocessedItems` as success); a retried batch with a new `$now()` writes a second fact, so OR and `cascade='all'` consumers run twice; nothing fences the batches by generation, so a zombie `run_task` writes facts after a Stop; a crash between batches leaves the facts of a task that ends `failed`.
- **The status first, with a "facts owed" mark, and the facts written by the dispatcher** (an outbox): it lifts the cap without those failure modes but changes invariant 12 and Rule 41. Deferred until someone needs it (a whole dbt project as one task, with one asset per model).
- **A run limit derived from the task limits, or kept alive by a sweeper heartbeat:** a pause without end, a restart and a retry after a decision all break a derived limit, which comes out at a year for almost every DAG anyway.
- **A `wait_for` default derived from the cadence of the awaited assets:** the cadence says how often an asset is written, not how late a fact may arrive; Airflow's sensors and Azure Data Factory's window dependencies also default to 7 days.
- **A run's history kept 31 days from each write:** a run that lives longer loses its rows while it runs. The console's 90 days match how long Step Functions keeps an execution's history; a history of years belongs in an export.
- **Timeline events with the history's long TTL:** they would take most of the table's space.
- **Shortening the history's TTL to 90 days once the run is answered:** it saves about 2% of the cost, and needs a reset in passes, its record on the run row and a condition on `run_version`: one more class of races.
- **A 1.2 run's graph inferred from its task rows instead of its snapshot:** that graph lacks the task types, trigger rules and groups.
- **A deadline after which a stopped row becomes `aborted`:** no common orchestrator holds a run open while it waits for a restart, and a restart stays possible after the run has ended.
- **Ending a run at the first final failure, as the default or an option** (what 1.2 did): the run showed `FAILED` while other tasks' wrappers went on working.
- **A `dependency_wrapper` stub that fails with a hint:** a leftover to keep; the console's mark and the list from `polyris-up` show the same thing.
- **Adopting 1.2's waiting rows during the upgrade, or writing run rows for 1.2 runs:** code for 1.2 runs that no later release uses, for a gap that closes when their rows expire.
- **A direct upgrade from 1.1.4:** it would keep the 1.1.4 compatibility code another release.
- **A 1.3 with only the removals, and rows in 1.4:** two upgrade windows instead of one.
- **2.0 instead of 1.3.0:** a major version spent on an internal rewrite before there are users; the "Breaking" block warns where the number does not.

## Out of scope

An `on_failure` hook in the DSL; a fail-fast option; branching, mapping and short-circuiting steps; freshness checks on awaited assets; a sweeper interval under 5 minutes; and what ADR #130 deferred (queue-based fan-out, subscriptions keyed by partition, a producer run id on each fact, a share of the sweeper's budget per step).

## Risks

- **Logic moves from Step Functions `Retry` into Lambda code, and races into the Lambda.** Answered by write-then-start, derived execution names, a sweeper check for every status in between, and a harness that interleaves at the boto3 boundary (*Tests*).
- **Every start goes through one Lambda.** The System status shows a stopped stream consumer (§6), and a lost hint costs at most the run row's next check (§7).
- **A burst of `StartExecution` calls on a wide fan-out.** A throttled start stays `deps_ready` and due; one that keeps failing warns once and fails at its deadline (§5).
- **The sweeper's queue holds a run row per unfinished run, each check a full pass.** One pass per run per sweep, earliest due first, and the oldest overdue row in the self-check (about 74 checks of 2,000-row runs fit one sweep).
- **A race can remove a row's due time.** Every full pass judges each row from the row itself and puts back the due times that differ; the run row stays due while a row is unfinished (invariant 9).
- **A full pass reads every row of its run** (about N² reads per run, §8); an asset wake is a narrow pass (§7).
- **Concurrent passes cancel each other's transactions on the run row.** A conflict is retried within the budget, and a row a pass leaves is no lost hint (§7).
- **One broken run fails its pass at every check.** The sweeper moves its due time by the backoff and warns, so it does not hold the budget (§7).
- **A record that keeps raising a transient error holds its shard for up to 24 hours.** The lost-hint warnings and their count show it (§6).
- **A fact recorded during the upgrade for a push consumer that waits for its redeploy.** The consumer's run fails at once, and its deterministic name keeps the catch-up from starting it again: re-run that date by hand.
- **A definition refers to specs never written** (after `polyris-down` and `polyris-up`, items deleted by hand, or a `--dry-run` template applied by other tooling). Its runs fail at `Start_Run` with a warning; `polyris-deploy` writes the items again.
- **Every run that starts on one day writes to one partition of `run-start-index`.** It holds run rows only, and a pass writes a summary only when it changed (§4); a schedule burst of about 350 writes a second on one start day did not throttle.

## Tests

The harness comes first, before the code it tests, and each test before the code that turns it green. The tests that pin a rule are named next to it above; the invariants are checked in `test_row_invariants.py` (`tests/backend/coordination/`), the writers in `tests/sdk/test_task_row_writers.py`, the upgrade in `test_upgrade.py`, `test_up.py` and `test_cfn_changeset.py`.
- **The harness interleaves at the boto3 boundary.** It wraps each component's client and pauses after a read returns or before a write is sent, with no hook in production code (Principles #11 and #14). It can drop or delay a record of the tasks table's stream (`drop` loses matching records, `delay` holds them), expire TTL rows with their `REMOVE` records, return a partial `BatchGetItem`, and run two passes over one run at once. It models `State.RetryCount`, `Execution.RedriveCount` and `States.DataLimitExceeded`.
- **Invariants are staged.** Each invariant is checked from the stage of the build that adds its mechanism; a scenario that needs a later mechanism is skipped until then, with that reason (`needs_binding`). Every check is shown to flag a planted violation, and invariant 8 is checked in both directions (§2).
- **Liveness at the end of a scenario.** Once `rows-core` is bound, the harness ends the failures the scenario injected, finishes the work still running, moves the clock past every deadline and sweeps until nothing changes. Then every run has ended or is paused, or a row waits for a decision with a due time.
- **Scale** rests on about 200 tasks in the harness and an estimate of the declared maximum from AWS's prices and quotas (§8); the game day (a `run_task` stopped in the AWS console, the mapping disabled, a record that keeps raising, `StartExecution` denied, throttling, a pause with a fact, a restart during a start) runs live.

## Probed AWS behaviour

Before the build, each AWS behaviour the design rests on was probed on a scratch stack (2026-11-18), and the end-of-execution rule on 1.3.2 in a dev account (2026-11-25). Code and tests cite these results by their ids, as "TR-0 B2"; the coordination harness models them (`tests/backend/coordination/sfn_runtime.py`, `stream_filters.py`).

- **A1.** A new index and a stream on `pipeline-tokens`, the new table and the deletion of eight state machines go through in one CloudFormation update, and its rollback restores the table.
- **A2.** The deletion of a Standard state machine waits for its `RUNNING` executions, and `ListExecutions` and `StopExecution` work on a state machine being deleted; its deletion ends about a minute after the stop.
- **A3.** CloudFormation reports the table updated while `run-start-index` is still being built: about 8 minutes for 100,000 rows.
- **B1.** Each attempt of a `lambda:invoke.waitForTaskToken` state brings a new token, `State.RetryCount` counts the attempts, `State.EnteredTime` stays the same for every retry, and an earlier token is refused with `TaskTimedOut`.
- **B2.** A Task whose result passes 256 KB fails with `States.DataLimitExceeded`; a `Catch` that names it, and one on `States.ALL`, both take it.
- **B3.** The SDK integration names the error `DynamoDb.TransactionCanceledException`, with the reasons in its cause, and a success transaction with a 200 KB item goes through.
- **B4.** A redrive of a failed run runs no `Start_Run` (the run fails after its `Parallel`, so it fails again at once); a redrive of an aborted run runs `Start_Run` again with `RedriveCount` 1 and `RetryCount` 0.
- **B5.** A work state that times out on a `.sync` integration stops its job within 15 to 60 seconds for Glue, ECS, Batch, Athena and a nested execution; EMR was not probed.
- **B6.** `DescribeExecution` shows a new execution in under 250 milliseconds.
- **C1.** The four filter patterns of §7, on a live mapping: of 25 writes exactly the 11 expected records passed, and no change from one final status to another, TTL write, `output#` row, warning row or deletion did.
- **C2.** An `anything-but` on the old image's status matches no insert, so `Start_Run`'s task-row inserts wake nothing; a mapping started at `LATEST` missed the records of its first two minutes, and one disabled and enabled again lost none.
- **C3.** `LastProcessingResult` reads OK again at the next healthy batch while one shard keeps retrying a record, so the lost-hint count carries that signal (§6).
- **C4.** DynamoDB stores the number `1.0` as `1` (§8), and `run-start-index` took about 350 writes a second on one start day without throttling.
- **Scale.** `Start_Run` wrote a run of 2,001 rows in about 17 of its 300 seconds; one pass over 2,000 rows took 2.2–2.6 seconds at 256 MB; a sweeper check of a waiting 2,000-row run took 2.6 seconds, 74 checks a sweep; 2,000 rows that finish at once drained from the stream in about 75 seconds with 4 shards.
- **End of an execution.** The pattern of `ExecutionEndRule` passed `events:TestEventPattern`; live, a run whose execution was stopped as the AWS console stops it carried the stop mark 1.3 seconds later, and the engine's own stop (`Polyris.Stopped`) made no event pass for the task.
