# ADR #127 — Pre-deploy resource override check in `polyris-deploy`

**Context.** The existence check (ADR #126) verifies that referenced AWS resources exist. A second class of deploy-time problem exists: a task may reference a resource that exists but whose current default configuration silently differs from the values declared in the DAG. For example, a Glue job's default `WorkerType` may be `G.1X` while the DAG declares `G.2X`; a Batch job definition may list an argument in `NonOverridableArguments` that the DAG passes, causing Glue to silently ignore it at runtime. These divergences produce no error — they are silent runtime overrides that are only discovered during execution.

**Decision.** Add an advisory override check to `deploy_pipeline`, running after the existence check. For Glue, ECS, and Batch tasks, the check fetches the current resource defaults from AWS and compares them against the declared task parameters. It reports: parameters that differ from the resource default (potential silent runtime overrides), Glue arguments in `NonOverridableArguments` (silently dropped by Glue at runtime), and declared parameters that match defaults (can be omitted for a cleaner DAG). The check is advisory only — it never aborts deploy.

**Key design choices.**

*Advisory, never abort.* The override check is wrapped in a broad `except Exception` in `deploy.py`. A code bug in a checker, an unexpected AWS response shape, or any transient error must not block the deploy. The existence check already confirms the resource is reachable; the override check is best-effort comparison. The exception message includes the exception class name to aid post-hoc triage.

*`failed_refs` passthrough.* `ResourceCheckResult.failed_refs` from the existence check is passed to `check_resource_overrides` as the `failed_refs` argument. Resources that were confirmed missing or IAM-inaccessible during existence check are skipped in the override check without a second API call. Throttle and BotoCoreError are excluded from `failed_refs` because they are transient — the resource may still exist and the override check surfaces a fresh `unverified` entry if it also cannot reach the service.

*`OverrideCheckResult.expired_token` flag.* When `ExpiredTokenException` fires mid-loop, the flag is set on the result and propagated to the output message. The user sees "credentials expired mid-check; re-authenticate and re-run polyris-deploy" rather than the generic "access denied, throttled, or other transient error", which would lead them to audit IAM policies instead of refreshing their session.

*Unknown ECS container name is skipped, not compared against an empty base.* When a `containerOverrides` entry names a container that is not in the task definition's `containerDefinitions`, the check skips that entry. Comparing against an empty base dict would produce a spurious conflict for any declared `command` (actual would be `[]` rather than "container not found"). The advisory check cannot produce a meaningful comparison without a baseline.

*ECS task-level and per-container cpu/memory are both checked.* The ECS `overrides` struct supports task-level fields (`overrides.cpu/memory`) and per-container fields (`containerOverrides[*].cpu/memory`). Both are compared against the task definition. Task-level `cpu`/`memory` are compared against the task definition's top-level `cpu`/`memory` string fields using the same int normalization as container-level fields (both sides use CPU units and memory in MiB — 1 vCPU = 1024 CPU units, 1 GiB = 1024 MiB).

If the task definition has no top-level `cpu`/`memory` (EC2 launch type without explicit task-level resource limits), the check emits a `not checked:` per-parameter line under the resource header. When this is the only finding for a task, it appears in the success block; when other conflicts are also present for the same task, it appears inline alongside those conflicts in the warning block. If the declared or task-definition value is non-numeric (not a valid integer or numeric string), the comparison is silently skipped — no diff and no scope note; this applies to both task-level and container-level fields.

*Glue arguments not in `DefaultArguments` are not reported.* The checker compares each `glue_arguments` entry against the job's `DefaultArguments` dict. If an argument is absent from `DefaultArguments` (and also not in `NonOverridableArguments`), it is silently skipped — no differs, no matching, no output. Rationale: an argument absent from the job's defaults is a new addition by the DAG; there is no baseline value to compare against. This means a misspelled argument name that doesn't match any default will not be flagged. This is a V1 scope limit.

*Batch parameters not in job definition `parameters` are not reported.* Similarly, `batch_parameters` entries absent from the job definition's default `parameters` dict are silently skipped. A new parameter is an intentional addition; there is no default to compare against.

*EMR and SageMaker excluded by design.* `emr_step` is submitted dynamically per-run; there is no static job-level default to compare against. SageMaker is not yet implemented.

*`_OverrideEntry` NamedTuple instead of a bare 5-tuple.* Each entry in `_OVERRIDE_INFO` uses a named tuple (`kind`, `service`, `ref_attr`, `fetcher`, `checker`) so callers and tests access fields by name rather than by magic index.

*Tasks with a different IAM role are skipped.* When `task.role != "same"`, the override check skips the task entirely — the deploy-time session cannot assume a different role, so the task's override parameters are neither fetched nor compared. This is consistent with the existence check (ADR #126) which also skips cross-role tasks. The skipped count is tracked in `OverrideCheckResult._skipped` and shown in the success tick when non-zero.

*No advisory message for unknown ECS container name.* When a `containerOverrides` entry names a container not in `containerDefinitions`, the check skips it silently. Surfacing an advisory would require distinguishing a user typo from a valid cross-definition container reference — out of scope for V1 of the check. The skip-without-output choice prevents a re-introduction of the spurious-conflict bug it replaced.

*`unverified` deduplicates by resource; `reports` does not.* When tasks T1 and T2 both reference the same resource and the fetch fails, only T1 appears in `result.unverified` — T2 is silently skipped via `unverified_seen`. The user sees one unverified entry per unique resource. `result.reports` does NOT deduplicate: when T1 and T2 both reference the same Glue job and the fetch succeeds, the checker runs for both tasks and may produce two separate `OverrideReport` entries for the same resource (one per task, potentially with different declared values). This is intentional — two tasks can declare different override values against the same resource default, and both are worth reporting.

A user seeing the same resource name appear twice in the output is seeing reports for two distinct tasks. This asymmetry is by design: `unverified` is per-resource (the resource is unreachable — once is enough to surface it); `reports` is per-task (each task's declared values are independently compared against the same resource default and may differ, so deduplication would silently drop half of the information).

*`ParamConflict.declared` is typed `Any` but conventionally differs by service.* For ECS cpu/memory, `declared` is an `int` (string inputs are normalized via `int()`). For Batch parameters, `declared` is a `str` (all values are coerced with `str()`). For Glue and ECS command, `declared` is whatever the DAG declared (typically `str` or `list`). Callers comparing `conflict.declared == "1024"` for ECS cpu would receive `False` — compare against `int(1024)` instead. This asymmetry mirrors the AWS API conventions: ECS cpu/memory are always integers; Batch parameters are string key-value pairs.

**IAM requirements.** The override check calls `glue:GetJob`, `ecs:DescribeTaskDefinition`, and `batch:DescribeJobDefinitions`. These run with the same deploy-time credentials as the existence check. Access-denied converts to `unverified`, not an abort. The deploy role requires these actions in addition to the existence-check actions listed in ADR #126; the IAM requirement is documented in root `CLAUDE.md` under Deployment.

**Consequences.**
- `check_resource_overrides` makes one additional AWS API call per unique Glue/ECS/Batch resource. Deduplication (same resource in multiple tasks = one fetch) limits the call count. The fetch result is cached for the duration of one DAG's check.
- `OverrideCheckResult` carries `expired_token: bool` to let the output layer distinguish credential expiry from IAM denial.
- `OverrideCheckResult._verified` counts unique resources *successfully fetched*, not total attempts. This differs from `ResourceCheckResult._checked`, which counts total attempts including failures. The print layer gates the success tick on `_verified > 0` to avoid claiming "no issues" when no resource was actually verified. When `_verified == 0` and `_skipped > 0` (all override-checkable resources had existence failures), the print layer emits a warning rather than silence so the operator knows the override check ran but was fully skipped.
- `_OVERRIDE_CHECKERS` completeness is enforced by `test_override_checkers_covers_all_task_types` — adding a `TaskTypeLiteral` without updating the dict fails the test immediately. The checker entries for Glue, ECS, and Batch are auto-derived from `_OVERRIDE_INFO` via a dict spread — only task types without override params (SFN, Lambda, Athena, etc.) need a manual `None` entry. The comment in `_OVERRIDE_INFO` documents the two paths explicitly.
