# Backend Implementation

## Overview

The backend consists of:
- **Step Function state machines** (16 total) — 13 templates + 3 test SFNs
- **Lambda functions** (6) — Evaluation, queries, API, assets, and bootstrapping
- **DynamoDB tables** (8) — State and metadata storage
- **EventBridge rules** - Auto-registration on deploy, external asset events

**Generated constants & enums.** Status/trigger/backfill enum families and the
backfill error-code registry are defined once in `polyris/constants.py` and
code-generated by `polyris.codegen.sync_enums` into each Lambda's
`constants_generated.py` and the UI's `ui/src/generated/enums.ts`. The Lambdas
import the generated module (the per-Lambda `constants.py` re-exports it);
`make check-generate-enums` / `sync-constants` gate drift in CI. Don't hand-edit
the generated files or duplicate an enum — edit `constants.py` and regenerate
(DESIGN_DECISIONS #72/#83/#93/#94).

## Step Function Helpers

### 1. sf_dependency_wrapper

Main wrapper that orchestrates task execution:

```
Start
  │
  ├─▶ Generate_IDs
  │
  ├─▶ Call registration_helper (register task + subscriptions)
  │
  ├─▶ Check_Skip_Signal (was task already skipped?)
  │
  ├─▶ Check_Has_Dependencies
  │     │
  │     ├─▶ Yes: Wait_For_Task (waitForTaskToken)
  │     │        └─ Woken by notify_dependents Lambda
  │     │
  │     └─▶ No: Continue
  │
  ├─▶ Check_Deps_Signal (pass/block/skip)
  │     │
  │     ├─▶ pass: Continue execution
  │     ├─▶ skip: Mark skipped, notify dependents
  │     └─▶ block: Mark upstream_failed
  │
  ├─▶ Check_Wait_Before (optional delay)
  │
  ├─▶ Call run_task_helper (execute actual task)
  │
  ├─▶ Emit_Asset_Events (if outlets defined)
  │
  └─▶ Done
```

### 2. sf_registration_helper

Registers task and subscriptions at runtime:

```
Start
  │
  ├─▶ Check if already registered (idempotent)
  │
  ├─▶ Register_Task (DynamoDB: pipeline_tokens)
  │     - execution_name, task_name, pipeline_name
  │     - status: waiting
  │     - dependencies, trigger_rule, alerts
  │
  ├─▶ Record_Start_Event (DynamoDB: task_events)
  │
  ├─▶ Create_Subscriptions (DynamoDB: dependency_subscriptions)
  │     - For each dependency: store wait_token
  │
  └─▶ Return dependency check result
```

### 3. sf_run_task_helper

Executes the actual task:

```
Start
  │
  ├─▶ Check_Execution_Paused
  │     └─▶ If paused: Call sf_pause_waiter, wait for resume
  │
  ├─▶ Update_Status_Running (DynamoDB)
  │
  ├─▶ Save_Task_ARN (for UI linking)
  │
  ├─▶ Read_Upstream_Outputs (data passing from dependencies)
  │
  ├─▶ Route by task_type:
  │     │
  │     ├─▶ sfn: startExecution.sync:2
  │     ├─▶ lambda: lambda:invoke
  │     ├─▶ glue: glue:startJobRun.sync
  │     ├─▶ ecs: ecs:runTask.sync
  │     ├─▶ athena: athena:startQueryExecution.sync
  │     ├─▶ emr: elasticmapreduce:addStep.sync
  │     └─▶ batch: batch:submitJob.sync
  │
  ├─▶ ON SUCCESS:
  │     ├─▶ Save_Success (DynamoDB: pipeline_tokens)
  │     ├─▶ Emit_Task_Finished (DynamoDB: task_events)
  │     ├─▶ Notify_Dependents (SFN: notify_dependents helper)
  │     ├─▶ Emit_Asset_Events (DynamoDB: asset_events, if outlets)
  │     ├─▶ Notify_Asset_Subscribers (Lambda, if outlets)
  │     └─▶ Send_Pipeline_Success (orchestrator token, if last task)
  │
  └─▶ ON FAILURE:
       ├─▶ Emit_Task_Finished_Failed (DynamoDB: task_events)
       ├─▶ Notify_Dependents_Failed (SFN: notify_dependents helper)
       └─▶ Send_Pipeline_Failure (orchestrator token)
```

### 4. sf_pause_waiter

Saves pause token for callback-based resume:

```
Start
  │
  ├─▶ Save pause_token to DynamoDB
  │     - status: waiting_paused
  │     - pause_token: task token from parent
  │     - paused_at: timestamp
  │
  └─▶ Complete (parent waits for SendTaskSuccess)
```

Called by run_task_helper when pipeline is paused. Parent SFN waits up to 12 hours for resume callback.

### 5. sf_failure_handler

Runs after a task is terminally failed (wrapper catches the failure). Updates
state, notifies dependents, and sends the follow-up alerts as a single batch
through the notify Lambda.

```
Start
  │
  ├─▶ Ensure_Pipeline_Execution_Short (Pass)
  │
  ├─▶ Truncate_Error (Pass — prevent DynamoDB item-size limit)
  │
  ├─▶ Update_Status_Failed (DynamoDB updateItem)
  │
  ├─▶ Notify_Dependents (startSyncExecution → notify_dependents SFN)
  │
  ├─▶ Check_Is_Upstream_Failed (Choice)
  │     └─▶ upstream_failed tasks skip alerts (root cause already alerted)
  │
  ├─▶ Send_Alerts (lambda:invoke → notify Lambda, batch)
  │     └─▶ one call with {pipeline_name, failure}; the Lambda reads alert_config
  │         and posts to every enabled channel (Slack restart-only + PagerDuty)
  │
  ├─▶ Check_Orchestration_Token (Choice)
  │
  └─▶ Send_Task_Failure (sendTaskFailure callback to the wrapper)
```

Collapsed from the older multi-state fan-out (per-channel states + separate
alerter SFNs) to a single `Send_Alerts` Lambda call in Stage 1a (ADR #103).

### 6. sf_restart_task_helper (EXPRESS)

Restarts a failed task:

```
Start
  │
  ├─▶ Get task info from DynamoDB
  │
  ├─▶ Reset status to 'waiting'
  │
  ├─▶ Re-register subscriptions
  │
  ├─▶ Check dependencies again
  │
  └─▶ If ready: trigger run_task_helper
```

### 7. sf_restart_wrapper (EXPRESS)

Restarts the wrapper execution:

```
Start
  │
  ├─▶ Get original wrapper input
  │
  ├─▶ Start new wrapper execution
  │
  └─▶ Return new execution ARN
```

### ~~10. sf_register_on_create~~ — Removed (v69.1)

Registration is handled by the `register_pipeline` SFN at deploy time via `polyris-deploy`. See ADR #24.

### 8. sf_notify_dependents_helper (EXPRESS)

Invoked when a task completes (success, failed, skipped, aborted).
Replaces EventBridge-based notification (pre-v51) with SFN-based approach
for full visibility in execution history.

**Express workflow** — no waitForTaskToken or .sync calls, runs in seconds.
Execution history available via CloudWatch Logs (level: ALL).
Parent Standard workflows call via `startExecution.sync:2` (AWS handles Express target).

```
Task Completion (run_task/failure_handler/console_api)
  │
  └─▶ sfn.startExecution(notify_dependents_helper)
        │
        ├─▶ Query subscriptions for this task
        │
        ├─▶ For each subscriber (Map state, MaxConcurrency=10):
        │     │
        │     ├─▶ Get subscriber record (tokens, dependencies, trigger_rule)
        │     │
        │     ├─▶ evaluate_deps Lambda:
        │     │     ├─ BatchGetItem: get all dependency statuses
        │     │     ├─ BatchGetItem: skip_origin, only if a dep is skipped (ADR #115)
        │     │     ├─ Check pipeline pause status
        │     │     └─ Evaluate trigger_rule (5 rules — ADR #117)
        │     │
        │     ├─▶ Route based on evaluation (verdict, ADR #115):
        │     │     ├─ is_ready: Signal_Ready → Update status → Delete subscription
        │     │     ├─ verdict='skip': Signal_Skip → Mark skipped, notify dependents
        │     │     │     (rule's condition never occurred — not an error)
        │     │     ├─ verdict='upstream_failed': Signal_Blocked → Update status → Delete subscription
        │     │     └─ is_paused: Mark_Waiting_Paused (save wait_token for resume)
        │     │
        │     └─▶ Cleanup processed subscription
        │
        └─▶ Done
```

**Entry points:**
- `run_task_helper` → Notify_Dependents (success)
- `failure_handler` → Notify_Dependents (failed)
- `console_api` → skip_task, fail_task, mark_success, stop_task (via notify_dependents_via_sfn)
- `slack.py` → slack_action_skip, slack_action_fail, slack_action_success (via notify_dependents_via_sfn)

### 9. sf_notify_asset_consumers_helper (EXPRESS)

Processes asset materialization and triggers subscribed pipelines.
Replaced Lambda `asset_trigger` in v55 — now pure Step Functions for transparency.

**Express workflow** — DynamoDB queries + fire-and-forget startExecution.
Execution history available via CloudWatch Logs (level: ALL).

```
run_task_helper → Notify_Asset_Consumers_SFN (async StartExecution)
  │
  ├─▶ Query asset_subscriptions for consumers
  │
  ├─▶ For each consumer DAG (Map, concurrent):
  │     │
  │     ├─▶ Check self-trigger (prevent cycles)
  │     │
  │     ├─▶ Check operator (OR or AND)
  │     │
  │     ├─▶ If OR: StartExecution immediately
  │     │
  │     ├─▶ If AND:
  │     │     ├─▶ PutItem to queued_asset_events (conditional)
  │     │     ├─▶ UpdateItem counter (atomic ADD)
  │     │     ├─▶ If count >= required: acquire lock
  │     │     └─▶ StartExecution with all assets
  │     │
  │     └─▶ Deduplication via execution name
  │
  └─▶ Done
```

## Lambda Functions

### 1. console_api

REST API handler:

**Endpoints:** 27 free (OSS build), 63 in the full build. Free routes cover
pipelines, tasks, executions, assets, runs, and notifications. Paid (Team)
routes add backfill, alert config, PATs, and observability.

### 2. evaluate_deps

Called by `notify_dependents` SFN helper via `lambda:invoke`.

Evaluates whether a subscriber task should start based on all upstream statuses:

- `BatchGetItem` — fetch all dependency statuses in one call
- `BatchGetItem` — fetch `skip_origin`, only when a dependency is `skipped` (ADR #115)
- Evaluate `trigger_rule` (5 rules — ADR #117; see
  `docs/features/DSL.md#trigger-rules`)
- Check pipeline `paused` status
- Returns: `{is_ready, is_blocked, is_paused, deps_satisfied, verdict, reason, dep_statuses, counts}`
  — `verdict` (`ready | wait | skip | upstream_failed`, ADR #115) drives the routing above

### 3. query_subscriptions

Called by `notify_dependents` SFN helper. Required because DynamoDB Query
has no optimized SFN integration with JSONata.

- Queries `dependency_subscriptions` table for all tasks waiting on a given completed task
- Returns: `{subscribers: [{task_name, wait_token, ...}]}`

### 4. check_assets

Called by `registration` SFN helper for tasks with `wait_for` asset dependencies.

- Checks `asset_events` table for asset freshness
- Returns whether all required assets are fresh enough

### 5. notify_asset_subscribers

Called by `run_task` helper when a task with `outlets` completes.

- Writes to `asset_events` table
- Queries `asset_subscriptions` for consumers
- Sends `SendTaskSuccess` tokens to waiting tasks (PULL model)

### ~~7. extract_sfn_metadata~~ — Removed (v69.1)

Registration handled by `polyris-deploy` via boto3 + inline `Register_Pipeline` state.

## DynamoDB Tables

### pipeline_tokens

Task state tracking:

| Attribute | Type | Description |
|-----------|------|-------------|
| execution_name | PK | Unique task execution ID |
| task_name | S | Task identifier |
| pipeline_name | S | Pipeline identifier |
| status | S | Current status |
| dependencies | L | List of dependency task names |
| trigger_rule | S | When to trigger |
| started_at | S | ISO timestamp |
| finished_at | S | ISO timestamp |
| error | S | Error message (if failed) |

**Canonical output store (data passing).** This table also holds each task's
*output* under a stable, partition-scoped key `output#{pipeline}#{task}#{date}`
(written by `Save_Canonical_Output` on success; large payloads spill to S3 with
a pointer). Downstream tasks read their upstreams' outputs from these keys
(`Read_Upstream_Outputs` → `Prepare_Task_Input` in the run_task helper) — this
is how data flows between tasks, not in-process. The key is independent of the
per-run `execution_name` rows, so an auto-skipped task's prior output survives
incremental backfill. Entries carry a TTL, so deep historical backfills may find
an ancestor's output expired. Existence of `output#…#date` is also the signal
used to decide whether an upstream is "ready" for a partition during
lineage-aware backfill (see ARCHITECTURE.md → Backfill).

### dependency_subscriptions

Dependency callbacks:

| Attribute | Type | Description |
|-----------|------|-------------|
| dependency_key | PK | "task-execution-short" |
| subscriber | S | Subscriber task name |
| wait_token | S | Step Functions task token |
| subscriber_execution | S | Full execution name |
| trigger_rule | S | Subscriber's trigger rule |

### task_events

Task history:

| Attribute | Type | Description |
|-----------|------|-------------|
| task_run_id | PK | Task execution ID |
| event_time | SK | ISO timestamp |
| event_type | S | STARTED, TASK_FINISHED, etc. |
| details | M | Event details |

### pipeline_registry

Pipeline metadata:

| Attribute | Type | Description |
|-----------|------|-------------|
| pipeline_name | PK | Pipeline identifier |
| sfn_arn | S | Step Function ARN |
| dag | S | JSON: nodes, edges |
| tasks | S | JSON: task definitions |
| schedule | S | Schedule expression |
| asset_schedule | S | JSON: asset trigger config |

### asset_events

Asset history:

| Attribute | Type | Description |
|-----------|------|-------------|
| asset_name | PK | Asset identifier |
| event_time | SK | ISO timestamp |
| date | S | Materialization date |
| source_pipeline | S | Producer pipeline |
| source_task | S | Producer task |

### queued_asset_events

AND trigger queue:

| Attribute | Type | Description |
|-----------|------|-------------|
| dag_date_key | PK | "dag_id#date" |
| asset_name | SK | Asset identifier |
| received_at | S | Event timestamp |
| ttl | N | Auto-delete timestamp |

### asset_subscriptions

Asset→DAG subscription mapping (PUSH model triggers):

| Attribute | Type | Description |
|-----------|------|-------------|
| asset_name | PK | Asset identifier |
| pipeline_name | SK | Consumer pipeline |
| sfn_arn | S | Consumer SFN ARN |
| operator | S | "OR" or "AND" |
| required_assets | L | All assets needed (AND logic) |
| ttl | N | Auto-delete timestamp |

## EventBridge Events

**Note:** As of v51, `task.completed` events are NO LONGER emitted via EventBridge.
Task completion notifications are handled directly by the `notify_dependents_helper` Step Function
which is invoked synchronously by run_task_helper, failure_handler, and console_api.

### task.failed (Deprecated - for monitoring only)

Previously emitted when task failed. Now used only for legacy monitoring/alerting integrations:

```json
{
  "source": "pipeline.tasks",
  "detail-type": "task.failed",
  "detail": {
    "task_name": "process",
    "execution_name": "process-2026-01-12-abc123",
    "pipeline_name": "acme-daily",
    "error": "Connection timeout",
    "date": "2026-01-12"
  }
}
```

### Asset.Materialized

**Note:** As of v55, internal asset triggers no longer use EventBridge. 
The `notify_asset_consumers` SFN helper handles pipeline-to-pipeline asset triggers directly.
External systems can trigger assets via `POST /api/asset/{name}/trigger`.

Event format reference (used internally by notify_asset_consumers):

```json
{
  "source": "pipeline.assets",
  "detail-type": "Asset.Materialized",
  "detail": {
    "asset_name": "processed/acme",
    "asset_uri": "s3://bucket/processed/acme/",
    "date": "2026-01-12",
    "source_pipeline": "acme-daily",
    "source_task": "process"
  }
}
```
